# rdd29 0.3.1

_Released 2026-08-14._

Patch. One security-relevant fix, no API change.

## Fixed — unbounded allocation from a wire-supplied Plex count

`ATMOSFrame.SubElementCount` and `BedDefinition1.ChannelCount` are Plex fields
read straight from the input. Plex escalates 8 → 16 → 32 bits, so **twelve
bytes** encode a count of `0x7FFF_FFFF`, and that count was passed directly to
`Vec::with_capacity`.

```text
08 0a 00 00 00 ff ff ff 7f ff ff ff
```

At roughly 112 bytes per `AnyElement` that is a reserve of about **240 GB**.

Found by a newly-added CI fuzz **run** (the gate previously only *built* fuzz
targets). AddressSanitizer aborted with:

```text
==5560==ERROR: AddressSanitizer: out of memory:
allocator is trying to allocate 0x37cbb80000 bytes
```

`0x37cbb80000` is 239.8 GB, matching the arithmetic above.

Both counts are now **rejected** — with a named `InvalidValue` error — when they
exceed what the remaining input could possibly contain.

The two ceilings are derived separately, from what each field actually costs on
the wire:

- `ATMOSFrame.SubElementCount` — every sub-element consumes at least one byte of
  the frame body, so the ceiling is the bytes remaining.
- `BedDefinition1.ChannelCount` — every channel description consumes at least
  **15 bits**, so the ceiling is `bits_remaining / 15`. An earlier revision used
  one bit per channel; that is a true bound but a needlessly loose one, and it
  admitted counts 15x larger than any input could describe.

A count above its ceiling cannot describe the element, so the input is
malformed and is rejected before anything is reserved.

## Why rejected rather than capped

Capping the reserve to the bytes remaining is the obvious fix and it is **not
sufficient**, for a reason worth recording: `Vec::with_capacity(2^31)` *succeeds*
under ordinary memory overcommit. The allocation is lazy, so nothing observable
happens until pages are touched — only a sanitizer refuses it outright.

That makes a cap verifiable by the fuzzer and by nothing else. A regression test
asserting "this does not allocate" passes just as happily against the unfixed
code, which is precisely the shape of test that lets a defect ship.

An explicit rejection is observable, so it can carry a real test.
`tests/oom_regression.rs` asserts the specific error and is mutation-verified:
removing the check turns it red, and the failure shows the old behaviour exactly
— the reserve silently succeeded and the parse then died on the first element
with `Bits { what: "ElementID", OutOfBounds { needed_bits: 8, remaining_bits: 0 } }`.

## Upgrading

No API change. A malformed frame that previously reserved an enormous buffer
before failing now fails immediately with `Error::InvalidValue`. Any input that
parsed successfully before still does.
