# DVB lockstep 10.0.0 — 2026-08-10

**Major.** Three things force it: the workspace MSRV moves to **1.95.0**, the
five lockstep crates cross the `mpeg-ts` `^0.3.1` → `^0.4` caret epoch, and
`dvb-si` tightens three section parsers in a way that rejects input they used
to accept. `dvb-conformance` additionally fixes an indicator that was
under-reporting real faults — including on this repository's own reference
fixture.

| crate | previous | new |
|---|---|---|
| `dvb-si` | 9.2.0 | **10.0.0** |
| `dvb-t2mi` | 9.2.0 | **10.0.0** |
| `dvb-bbframe` | 9.2.0 | **10.0.0** |
| `dvb-conformance` | 9.2.0 | **10.0.0** |
| `dvb-tools` | 9.2.0 | **10.0.0** |

`broadcast-common` is **not** in this set. It was ejected from the lockstep in
#862 and versions on its own API changes; it ships separately as **9.3.0** from
its own `broadcast-common-v9.3.0` tag.

## Breaking changes

### 1. MSRV is now 1.95.0

Raised from 1.86 (issue #949). The workspace had grown an MSRV *split*:
`webrtc-runtime`'s optional `media` feature needed rustc 1.88 via `rcgen`, and
containing that had cost a dedicated CI job, six `--exclude` lanes and a guard
script. Raising the floor deletes all of it. Per this project's policy an MSRV
raise is at minimum a minor bump, and here it rides an already-major release.

If you are pinned below 1.95.0, stay on 9.2.0 — it is unaffected and remains
installable.

### 2. `mpeg-ts` requirement crosses a caret epoch: `^0.3.1` → `^0.4`

`dvb-si`, `dvb-conformance` and `dvb-tools` now require `mpeg-ts` 0.4. A
published caret bucket that spans two epochs breaks consumers of **both** lines
(#858), so this cannot be a minor: a graph resolving `mpeg-ts` 0.3 and 0.4
together binds trait impls to the wrong copy, and the compiler reports errors
inside crates you never edited.

Diagnose with:

```bash
cargo tree -i mpeg-ts
```

Two versions in that output means a stale pin somewhere. The fix is to move
every crate in the table above together, in one commit.

### 3. `dvb-si` rejects trailing slack after the last loop entry

`PmtSection` (ISO/IEC 13818-1 §2.4.4.8), `SdtSection` (ETSI EN 300 468 §5.2.3)
and `AitSection` (ETSI TS 102 809 §5.3.4) now apply the post-loop length check
that `EitSection` already had.

Previously, a section whose **final** entry was truncated below its declared
header length parsed "successfully" with that entry silently absent — and
re-serialising it dropped the trailing bytes, so parse → serialize was not
byte-identical. That is a violation of this workspace's hardest invariant, and
it was silent: nothing in the API told you an entry had gone missing.

`AitSection` additionally rejects an `application_loop_length` that undershoots
the bytes actually available before `CRC_32` — the same silent-drop shape one
level up, since nothing follows the application loop in that section.

**What changes for you:** input that previously parsed now returns
`Error::BufferTooShort`. If you were relying on lenient parsing of truncated
sections, you must now handle that error. No fixture in this crate's suite
(`dvb-si/tests/fixtures/`, `fixtures/dvb-si/`) is affected — verified by
running the full fixture suite after the change — so a well-formed stream sees
no difference.

## `dvb-conformance`: `Continuity_count_error` was under-reporting (#956)

Indicator 1.4 treated **any** packet repeating the previous
`continuity_counter` on a PID as a legal duplicate. It never compared the
payload bytes.

ISO/IEC 13818-1:2023 §2.4.3.3 is explicit: in a duplicate packet each byte of
the original shall be duplicated, excepting only the PCR field, which may be
re-encoded. A packet that merely repeats the counter while carrying different
bytes is a **continuity error**, not a legal duplicate.

On this repository's own `fixtures/ts/m6-single.ts`, 73 packets fall in that
gap. They were being silently absorbed; they are now correctly counted. If you
track this indicator's absolute value, expect it to rise on real streams — the
new number is the right one, and the old one was hiding faults.

The check now delegates to the new shared `broadcast_common::ts_dup`
(`is_legal_duplicate_pair` / `check_duplicate`), which replaces three
independently hand-rolled and mutually disagreeing implementations of the same
spec paragraph (`dvb-conformance`, `media-doctor`, `ts-fix`). That
consolidation surfaced a second defect, in `media-doctor`: its `CcAnomalyCheck`
compared only the elementary-stream payload slice, so it would have accepted a
changed `splice_countdown` or OPCR as a legal duplicate, and it never enforced
the "two, and only two consecutive" cardinality rule at all — an unbounded run
of byte-identical repeats passed. Both are fixed in `media-doctor` 0.8.0.

A correction to the record: the original #956 note claimed `media-doctor`
"already implemented the payload-comparison rule correctly". It did not. That
claim is retracted in `dvb-conformance`'s CHANGELOG.

## Other changes

- **`dvb-si`** — `tables::sat`'s private `BitReader::read_u` now delegates to
  `broadcast_common::bits::BitReader`, which its `dvb-t2mi`/`rdd29`/`st291`
  siblings already used. Same bounds checking, same error shape, no behaviour
  change. The companion `BitWriter` stays hand-rolled on purpose: the shared
  writer validates value width and errors where several call sites here rely on
  silent truncation, so swapping it in would be a behaviour change this pass
  deliberately did not make.
- **`dvb-bbframe`** — README now documents that
  `CarryOverExtractor::feed_hem`/`feed_hem_into` emit no output for any HEM
  frame with `npd=true` (DNP reinsertion is not implemented) and that
  `CarryOverStats::npd_unsupported` counts those. No behaviour change; the
  caveat was already in rustdoc and only the README lacked it (#941).
- **`dvb-t2mi`** and **`dvb-tools`** carry no functional change beyond the MSRV
  and moving with the lockstep.

## Compatibility

Edition 2024, MSRV 1.95.0. `dvb-si`, `dvb-t2mi`, `dvb-bbframe` and
`dvb-conformance` build `--no-default-features` as `no_std` + `alloc` and are
cross-compiled for `thumbv7em-none-eabi` by CI. `dvb-tools` is a std-only
application and is not.
