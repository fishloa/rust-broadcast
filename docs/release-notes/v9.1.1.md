# DVB lockstep 9.1.1 — 2026-07-30

**Patch.** Floor four caret buckets that span `broadcast-common` epoch boundaries (#858). The independent crates that depend on the floored crates move with them. No functional or API changes.

## What a split bucket is

A caret requirement like `^0.3` on `mpeg-ts` resolves to any version `>=0.3.0, <0.4.0`. If 0.3.0 is built against `broadcast-common` 8 and 0.3.1 is built against 9, then `^0.3` spans the boundary. A consumer graph containing both `broadcast-common` 8 and 9 will have trait impls bound to the wrong copy, and the compiler will produce errors pointing at internals of a crate the consumer never edited.

Flooring to the first epoch-correct version in the bucket (`"0.3.1"`) closes the gap. This is a **patch**-class change: narrowing *within* the same caret bucket does not change which versions satisfy it.

## `broadcast-common` does NOT move

`broadcast-common` was ejected from the DVB lockstep in #862 (v9.1.0). It versions on its own API changes only. Nothing in this wave touches it, so it stays at 9.1.0.

## Compatibility

MSRV 1.86, edition 2024. Pure patch release — no breaking changes, no new API. Every crate in the table above is source-compatible with its previous published version.

## Diagnosing a mixed-version graph

```bash
cargo tree -i broadcast-common
```

If you see both 8.x and 9.x, you have a stale dep pin. The fix: bump every crate in the table above to the version listed, in one commit. `tools/check-published-dep-consistency.py` check 1 will report zero bucket-homogeneity violations against the published set once the wave is live.
