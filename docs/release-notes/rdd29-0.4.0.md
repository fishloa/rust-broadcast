# rdd29 0.4.0

_Released 2026-10-05._

Breaking release (0.3 -> 0.4) for the SMPTE RDD 29 Dolby Atmos bitstream parser and serializer. The break is one new public field, `align_bits`, on the two element structs. The rest is serializer and parser strictness: inputs that used to round-trip into different bytes, or that serialized `Ok` into a frame that `parse` would walk differently, are now rejected. If you construct `BedDefinition1` or `ObjectDefinition1` by struct literal you must add the field; if you only parse, you may see new errors on non-minimal `Plex` encodings.

## Breaking change: `align_bits` on `BedDefinition1` and `ObjectDefinition1` (#1114)

`BedDefinition1` and `ObjectDefinition1<'a>` gained `pub align_bits: u8`. RDD 29 gives its `AlignBits` byte-alignment padding no documented value (unlike this crate's other reserved fields, which all carry an explicit "set to X"), so it was previously discarded on parse and forced to zero on serialize; a stream with a nonzero value therefore did not round-trip. It is now preserved verbatim, the same treatment `st337` gives `Pf` (see `st337-0.3.1.md`). Neither struct is `#[non_exhaustive]`, so struct literals break. `BedDefinition1::new` and `ObjectDefinition1::new` set it to `0`.

```rust
// before (0.3): struct literal without the field
// after (0.4): add `align_bits: 0` (or prefer BedDefinition1::new / ObjectDefinition1::new)
```

If you use the `serde` feature, `BedDefinition1` derives `Deserialize` and the new field has no `#[serde(default)]`, so JSON written by 0.3 (which lacks `align_bits`) will not deserialize with 0.4.

## Stricter parse and serialize (all #1114 unless noted)

- **Non-minimal `Plex` escapes are rejected on parse.** A `Plex`-coded value that escalates to a wider container although it would have fit the previous, narrower level's direct range (RDD 29 section 3.4, "smallest container possible") now fails with the new `Error::NonMinimalPlex { field, value, width }`. It used to be accepted and re-serialized into different bytes. (`Error` is `#[non_exhaustive]`.)
- **`ObjectDefinition1::serialize_into` rejects inconsistent content** instead of silently misframing the output: a pan sub-block whose `decor_coef_prefix` and `decor_coef` disagree; an `AudioDescription` whose `flag_byte` `0x80` bit disagrees with whether `text` is present; and sub-block 0's `pan` being `None`. Previously only `ObjectDefinition1::new` checked the last one, so public-field construction could bypass it.
- **`AtmosFrame::serialize_into` checks pan sub-block counts against the frame rate.** An `ObjectDefinition1` element whose `pan_sub_blocks.len()` differs from the frame's `frame_rate.num_pan_sub_blocks()` (Table 7) is now an `Error::InvalidValue`; before, it serialized `Ok` into bytes that `parse` of the same frame would walk with the wrong loop count.

## Notes on two CHANGELOG "Fixed" entries

Two further CHANGELOG entries describe defects in the frame-level pan-sub-block check above: the mismatch error reported the element's index instead of the offending `pan_sub_blocks.len()` (release audit), and the Table 7 lookup ran even for a frame with a reserved `FrameRate` and no `ObjectDefinition1`, which broke the round trip (a CI fuzz finding). That check does not exist in `rdd29-v0.3.1`, so both were fixed before release and neither is a defect you could have hit in 0.3.1. The shipped behaviour is the one described above: the lookup runs only when an `ObjectDefinition1` needs it, and the error carries the offending count.
