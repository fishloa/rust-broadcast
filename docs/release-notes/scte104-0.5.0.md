# scte104 0.5.0

_Released 2026-10-05._

**Minor-epoch breaking release (0.x).** Three stored count fields are removed (they are now derived from the vector they describe), `Error` gains `FieldOverflow`, and one parser bug that rejected every conformant `insert_segmentation_descriptor_request_data()` message is fixed. Act if you set or read `descriptor_count` / `num_provider_avails` as fields. Requires [broadcast-common 9.4.0](broadcast-common-9.4.0.md).

## Dependency changes

```toml
-broadcast-common = { version = "9.3", default-features = false }
+broadcast-common = { version = "9.4", default-features = false }
```

## Breaking changes

1. `Error::FieldOverflow` (wrapping `broadcast_common::len::FieldOverflow`) is returned when a length or count does not fit its wire field, instead of the value silently wrapping (#1129). `Error` is `#[non_exhaustive]`.
2. `InsertDescriptor::descriptor_count`, `InsertAvailDescriptor::num_provider_avails` and `StartScheduleDownload::num_provider_avails` are no longer stored fields. Each is derived from its vec's length at serialize time (via `fit_u8`, so more than 255 items is an error, not a wrap) and is available as the method `descriptor_count()` / `num_provider_avails()`, which returns `usize`. A separately stored count could disagree with the vec: a stored count of 2 over one item misframed the next operation for a peer reading the declared count (audit run-09 S4-W1).

```rust
// before
let n = d.descriptor_count;               // field, and set on construction
let d = InsertDescriptor { descriptor_count: 2, /* ... */ };
// after: drop the field from struct literals, read the method
let n = d.descriptor_count();
```

## Behaviour changes

- `MultipleOperationMessage::new` saturates the stored `message_size` at `u16::MAX` for operation bodies too large for the 16-bit field (it used to overflow `u16` arithmetic: debug panic, release wrap). `serialize_into` recomputes the true size in `usize` and rejects one that does not fit (#1129).
- `MultipleOperationMessage::serialized_len` recomputes from `operations` instead of returning the cached `message_size`, which went stale as soon as a caller mutated the public `operations` vec (audit run-09 S4-W1).
- `ProvisioningService`'s `write_prefix` rejects a `component_mode` / `injector_component_list` pair that disagrees (`component_mode != 0` iff the list is `Some`), because the parser decides whether to read a list from `component_mode` alone and a mismatched pair would read back differently (audit run-09 S4-W1).

## Fixes

- `insert_segmentation_descriptor_request_data()`: `TAIL_LEN` (the fixed region after `segmentation_upid`) was 13 bytes, but Table 9-29 lists exactly 12 one-byte fields (`segmentation_type_id` through `sub_segments_expected`). Every conformant message, not an edge case, was rejected as one byte short. It is now 12 (#1068).
- `num_ops`, `operation.data_length`, `dtmf_length`, `segmentation_upid_length`, `service_count`, `number_of_DPI_PIDs` and the injector component-list audio/data counts were written with unchecked `as u8` / `as u16`, wrapping to a small value for 256 or more items (or 64 Ki or more bytes) while every item was still written. They are now range-checked (#1129).
