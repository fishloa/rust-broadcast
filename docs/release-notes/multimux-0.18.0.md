# multimux 0.18.0

_Released 2026-11-14._

Breaking-class release (0.17 -> 0.18): breaking API changes are listed below, and the crate's sibling dependencies move to new caret epochs.

Version: 0.17.0 -> 0.18.0.

## Breaking changes and migration

- `OutputAuthSpec::Forwarded` gained `trusted_proxies`; code constructing or exhaustively matching it must add the field. Behaviour: `X-Forwarded-User` is honoured only from a peer in `trusted_proxies` (default loopback); any other peer is `401`. A deployment whose proxy is not on loopback must list it.

```rust
// before
OutputAuthSpec::Forwarded { user_header, .. }
// after
OutputAuthSpec::Forwarded { user_header, trusted_proxies, .. }
```

- `DashWindowSegment` gained `public_seq` (the number a window segment is served under); struct-literal construction must set it.

- `Verifier::forwarded` is removed upstream; use `Verifier::forwarded_from(user_header, forwarded_for_header, trusted_proxies)`.

## Changed behaviour

- **Cold playlists now open in players that ignore Partial Segments (#1754).** A media-playlist request without `_HLS_msn`/`_HLS_part` made before the playlist holds a closed segment is held, through the blocking-reload wait and its timeout, until the first segment closes, then answered with at least one `EXTINF`; after the timeout it is `503` with `Retry-After`. ffmpeg, VLC, Frigate and go2rtc used to fail to open a cold stream. A request made before the route has announced its program is held too, up to the 5 s blocking-reload timeout, instead of an immediate `503`. A Low-Latency client's cold start now waits about one segment; `Config::hold_cold_playlist = false` (or `RouteHandle::with_hold_cold_playlist(false)`) restores the old immediate answers.
- A request carrying more than one `Authorization` header is answered `400 Bad Request` by the output-auth and admin gates; it used to authenticate on the first header and ignore the rest.
- The DVR also polls when the route's newest fMP4 init differs from the one it archived, so an init change rolls the period without waiting for the next closed segment.

## Added

- `OutputAuthSpec::Forwarded::trusted_proxies`: IPs and CIDR blocks allowed to set the forwarded-user header; omitted means loopback only (`127.0.0.0/8` and `::1`).
- `Config::hold_cold_playlist` (default `true`) and `RouteHandle::with_hold_cold_playlist`.
- `DvrRecorder::needs_poll_for_init`, `DashWindowSegment::public_seq`, `ProgramSegmenter::continue_after_reconnect`, and `DvrRecorder::poll_and_persist_inits` with `InitGeneration`.

## Fixed

- DASH, LL-DASH and Smooth answered `404` for every segment after a source reconnect; the MPD `startNumber` and Smooth fragment names now use the same public segment numbers the HLS playlist serves.
- DVR: a period roll that fails to open the new file no longer skips a period number; segments closed under one fMP4 init are archived under that init, not the next; segments closed but not yet archived survive a source reconnect; an evicted period's `pN.event.json` sidecar is removed with it.
- The catch-up playlist inserts `EXT-X-DISCONTINUITY` where the live tail does not continue the archive's numbering.
- The push `ReconnectEngine` resets its backoff only after a healthy connection, so a destination that accepts and then drops is backed off and eventually given up on.
- A catch-up request dropped mid-scan keeps its scan permit until the scan ends, so aborted requests cannot exceed `MAX_CONCURRENT_SCANS`.
- The HLS, DASH and Smooth pull sources take a fetch slot only when the fetch is due, so a sleeping retry or paced reload no longer holds back ready segment fetches.
- A blank or whitespace-only Bearer token is rejected at config validation (`output_auth.token`, `routes.input.auth.bearer_token`); `Authorization: Bearer ` used to authenticate.

## Other changes

- LL-HLS and TS-HLS share one HLS media-playlist implementation.
- The test-only feature is spelled `test-seams` everywhere (`webrtc-runtime/test-support` becomes `webrtc-runtime/test-seams`).
- The DASH period stitcher converts microseconds to ticks with `broadcast_common::timescale::from_micros`; rounding is unchanged.

## Also in this release

### Added
- `skills/multimux-basics/SKILL.md`: a Symposium agent skill shipped in the published package, so an AI coding agent working in a project that depends on `multimux` gets usage guidance covering route configuration, embedding the origin on tokio, the runtime admin API, the `multimux-cli` quick start, the scheme plugin registry, features and the pitfalls.
- `whep_media_sockets_per_ip` (config, default 8; `WhepRoute::with_media_sockets_per_ip`): the number of UDP media sockets a WHEP output binds per advertised IP, over which its viewers are spread round-robin. `0` is `ConfigInvalid`. More sockets spread the viewers' SRTP sends across cores at the cost of one file descriptor and one receive task each.
- `max_concurrent_warms_per_route` (config; `RouteHandle::with_max_concurrent_warms`, default 8): the bound on cold-egress warm-ups running on the blocking pool is per route, so one route's slow first Smooth plan or HLS segment scan no longer queues another route's.
- `max_blocking_reloads_per_route` (config; `HttpLimits::max_blocking_reloads_per_route`, default 1024): LL-HLS blocking-reload requests are budgeted per route instead of one listener-wide pool of `max_concurrent_requests / 4`, so a reload flood on one route cannot shed another's.
- LL-DASH renders through the shared DASH renderer (`manifest-ll.mpd` is the standard MPD model with the low-latency fields layered on: `ServiceDescription`/`Latency`, per-segment `availabilityTimeOffset`/`availabilityTimeComplete`, `minimumUpdatePeriod` at the chunk interval), so it gains what only `manifest.mpd` had: the Period split at a gap placeholder and at every init generation, each Period naming the versioned init segment its segments were cut under, and the SCTE-35 `InbandEventStream` declaration. A test pins that both flavours render the same Periods for a window through a gap and a codec change.
- `RouteHandle::has_active_tracks(program)`: `false` from the moment the source drops every muxable track until it announces one again; the segments and specs already published are unaffected. `DashWindowSegment` gained a `gap` field (a placeholder segment with no media bytes), so struct-literal construction must set it. A new dependency on `broadcast-dash` composes the Periods.
- Golden `fixtures/golden/hls/track-gap-live.golden`: the HLS media playlist and DASH MPD of a live route through video+audio, an empty track set and video+audio again.
- An RTSP pull places its tracks on one timeline with `transmux::TrackAligner`, the rule `broadcast-client` applies: the video track's times pass through, other tracks are offset from RTCP Sender Reports (or the PLAY `RTP-Info` when it names every track), and before either is known each track's first sample lines up with the video's first sample. Tracks whose RTP clocks start at unrelated offsets are now aligned by wall clock instead of each rebased to zero (#2380).
- An RTSP pull sends `TEARDOWN` (RFC 2326 §10.7) for a playing session when it is cancelled, before the connection closes; `RtspIngestSession::finish` queues it and the shared ingest scaffold writes what a finished session queued on cancel.
- An RTSP pull feeds interleaved RTCP on the negotiated RTCP channel to the track's depacketiser, which records Sender Report NTP anchors (`RtspIngestSession::rtcp_frames` counts them).
- `tests/it/ingest_drive_golden.rs` pins the WHIP and RTMP ingest event sequences (`fixtures/golden/ingest/`): the ordered `SessionEvent`s each real publish produces, the program and track specs it lands, and its final health — recorded at the session boundary the #2373 shared drive loop must reproduce. Regenerate with `UPDATE_INGEST_GOLDENS=1`.

### Changed
- The teletext subtitle follower's segmenting lives in `media_plane::segmenter::subtitle`; `source::split_subtitle` keeps the HLS rendition declarations and the pairing of pages to the route's `SubtitleServing`s (issue #2554).
- The HLS, DASH, Smooth, TS-over-HTTP, RTSP and SRT pulls map their `Timeouts` with `broadcast_client::Config::with_timeouts`; the five hand-written conversions (`read_us` x3, `ts_http::policy_config`, the SRT handshake mapping) are deleted (#2590).
- Building an output-auth verifier reports an unavailable OS random source (Digest) as `MultimuxError::Auth` instead of panicking (#2591).
- The audio follower's segmenting lives in `media_plane::segmenter::audio`; `source::split_audio` keeps the route-facing half: selectors and name from the route, and applying the follower's init segment and part target to the rendition's `HlsOrigin` (issue #2554).
- The SRT pull maps its connect bound onto the session's handshake bound through `SrtConfig::with_timeouts` instead of converting to milliseconds itself (#2514).
- Route and output code names the container as `transmux::Container` (issue #2554).
- The segmenters' shared publish queue (`PendingPublish`, `drain_publish_queue`, `part_entry`) lives in `media_plane::publish_queue` (issue #2554).
- A WHEP route binds up to 8 media sockets per advertised IP (viewers are spread over them round-robin) instead of one: with 1000 real WebRTC viewers the single socket's send path was the serial point of every SRTP stream (slowest viewer 54% of frames, p99 7.9 s); with 8 sockets every viewer receives 100% at p99 61 ms.
- The Smooth pull goldens run in the crate's own tests on a session clock 20 times faster than real time, so the deliberately missing fragment's retry backoff costs about 2.7 s of wall time instead of about 54 s; the goldens are unchanged.
- Every pull input's session queue is also bounded in bytes (`Config::max_queued_bytes`): 32 MiB for the live inputs (TS-over-HTTP, UDP, RTP, SRT caller, RTSP), 128 MiB (two maximum-size segments) for HLS, DASH and Smooth pull, instead of only the 100 000-event count.
- The session host yields to the runtime every 256 session events it hands to the driver, and the segmenter drives at most 512 queued samples per program per pass (`source::advance_route` yields between passes), so a large queued burst no longer holds a worker thread, or starves a current-thread runtime, for its whole length.
- The admin registry serialises add, remove and reload per route name (and case-insensitively) instead of computing the DVR archive floor under the registry-wide lock: a slow archive scan for one route no longer delays an admin change to another, a remove drains its route before releasing the name so a later add of that name reads the floor only afterwards, and a drain no longer holds the registry-wide lock (issue #2533).
- Smooth pull uses one process-wide HTTP client (one connection pool and TLS root store) instead of building a client per connection attempt (issue #2533).
- A segment served with SCTE-35 `emsg` boxes spliced in is spliced once per program (the last 16 are kept) instead of copied and rebuilt on every request (issue #2533).
- A listener-mode SRT route waiting for its Caller ends the wait when its cancel token fires, instead of relying on the supervisor dropping the future (issue #2533).
- The ingest scaffold and `source::advance_route` no longer require a session to be `Sync`, matching media-plane's `IngestSession` (`Send` only): `advance_route` runs its synchronous part when called and returns only the DVR drain future, which holds nothing of the driver (issue #2533).
- Smooth pull runs the relay `broadcast_client::Session` through the shared session host: the session owns manifest refresh, stream selection, chunk plans, track-id discovery, the synthesized init segment, timestamp rebasing, retry with `Retry-After`, live join and discontinuities. A manifest `<Protection>` or an encrypted fragment fails the attempt as the typed `MultimuxError::Session` naming `UnsupportedEncryption` (it was `MultimuxError::Encrypted`, which no source produces any more).
- WHEP viewers of a route share one UDP media socket per advertised IP (bound on the first viewer) instead of binding one each: every viewer's answer carries the shared address as its candidate, a receive loop asks `webrtc_runtime::media::SocketDemux` which viewer each datagram belongs to, and each viewer has a bounded queue that drops its newest datagrams when full without delaying the others. An ICE restart registers the new local ufrag with the shared socket (issue #2529).
- WHEP packetises each sample once per route instead of once per viewer: the route keeps the last 64 samples' RTP packets, and each viewer only sets its own sequence number, timestamp, SSRC and payload type on a copy before SRTP (issue #2529).
- A WHEP session's UDP receive buffer is 1500 bytes (one Ethernet MTU) instead of 64 KiB.
- Each admitted WHIP session runs on its own task, which owns its `MediaTransport`, its ICE/DTLS timers and its idle deadline; the route's publisher receives only the outcomes it must act on over a bounded channel, so a slow publisher or a stalled session no longer holds up another session's reads. A session whose publisher ends it is aborted, which closes its media socket at once. This completes the one-task-per-session work for RTMP and WHIP (issue #2525).
- RTMP: a session the route's publisher ends (a rejected feed, say) now has its read task aborted, so its connection closes immediately instead of staying open until the peer quits.
- A route configuration the `broadcast_client::Session` refuses (`InvalidConfig`, for example an unparsable RTP SDP) is `MultimuxError::ConfigInvalid` naming the session's field, and the route supervisor declares it permanent on the first attempt instead of retrying a configuration that cannot succeed.
- Raw RTP-over-UDP pull (SDP-described H.264/AAC) runs the relay `broadcast_client::Session` (`UdpConfig::sdp`) through the shared session host: the session routes packets by payload type and depayloads them; the host binds the socket with the route's socket options. `RtpUdpRoute` gains `with_socket` and `with_multicast_group`, mirroring `TsUdpRoute`.
- An RTSP DESCRIBE/SETUP/PLAY refusal (for example 503, 406 or 454) is reported as the `Protocol` error naming the method and the server's status, promptly, instead of a media-timeout error.
- A blocking-reload request beyond the trunk's waiter cap parks on `Trunk::waiter_slot_freed` instead of sleep-polling every 20 ms and re-rendering the playlist (#2523); the cap is no longer the 64-entry part ring.
- A WHEP viewer awaits the trunk's sample wake and reaps a silent viewer at the exact silence deadline instead of ticking every 10 ms and polling its cursor under the trunk lock (#2524).
- RTSP pull (`rtsp://` and `rtsps://`) runs the relay `broadcast_client::Session` through the shared session host: the session owns the RTSP engine, auth, keepalive, RTP/RTCP depayload, A/V alignment and the `TEARDOWN`; the host opens the TCP/TLS connection, writes what the session sends and sends the goodbye on cancel. The route's tracks are announced when PLAY is answered, as before; an answered `404` on DESCRIBE is still the permanent-failure `Protocol` error the supervisor counts.
- SRT caller pull runs the relay `broadcast_client::Session` through the shared session host (the session owns the handshake, ARQ and TSBPD; the host performs its connected UDP socket); listener mode is unchanged.
- TS-over-UDP pull (unicast and multicast) runs the same relay `broadcast_client::Session` through the shared session host: the session names the socket, the host binds it with the route's socket options (`SO_RCVBUF`, reuse, multicast interface as address or IPv6 index) and feeds each datagram to the session. A pre-bound socket is still consumed once and still cannot join a group.
- TS-over-HTTP pull runs one `broadcast_client::Session` in relay mode (`Config::relay()`) through a shared async session host (`source::client_host`): the session owns redirects, cookies, Basic/Digest/Bearer auth, the finite-body decision and the stall policy, and the host performs its HTTP requests with `reqwest`; the programme split of a multi-programme stream keys on each track's `program_number` as before.
- DASH-IF ingest sans-IO engine moved to `dash-runtime::ingest`; multimux keeps the axum glue.
- **BREAKING:** one HLS output, `output::hls::HlsOutput`, parameterised by `HlsFlavour` (`HlsOutput::low_latency(name)` for LL-HLS over fMP4, `HlsOutput::segmented(name)` for classic TS-HLS), replaces `output::llhls::LlHlsOutput` and `output::ts_hls::TsHlsOutput`; the `llhls` and `ts_hls` modules are removed (#2449). Config output names (`llhls`, `ts_hls`), playlist names and URLs are unchanged.
- The RTSP pull and the raw RTP/UDP source read SDP media sections through `transmux::sdp_track` (the rule `broadcast-client` already used): the played payload type is the first listed one with a usable `a=rtpmap`/`a=fmtp` (previously always the first listed, with the section's first `rtpmap`/`fmtp` whatever payload type they named), an H.264 section without `sprop-parameter-sets` is accepted with in-band parameter sets, an audio section whose `a=rtpmap` names another codec is rejected, and the H.264 coded size comes from the SPS. Recorded row by row in `fixtures/golden/sdp-tracks/multimux.txt`.
- HTTP pull auth (`ts_http`, `hls_pull`, `dash_pull`, `smooth_pull`) runs on `broadcast_client::auth::AuthState`: origin-scoped credentials, preemptive Basic/Bearer, and the one-shot Digest replay with cross-origin refusal are no longer re-implemented in `source::http_auth` (#2371). Each fetch works on its own clone of the state; an unanswerable Digest challenge now surfaces as the raw 401 response instead of `MultimuxError::Auth` (goldens in `source::http_auth` tests).
- The RTMP push builds its `onMetaData` with `transmux::on_metadata_body` and decides which tracks FLV can carry with `transmux::flv_track_kind`, so a file `FlvMux` writes and a stream the push publishes describe the same tracks the same way; the transport's own builder and codec check are gone. The published `onMetaData` now carries `audiosamplerate` from the AAC track and a `stereo` flag that follows its channel count (Adobe FLV v10.1 §E.5), and no longer the non-§E.5 `audiochannels`; the live body omits `duration` (it has no known length).
- The SRT push parses its `srt://` URL with `srt_runtime::SrtUrl` and applies only its own policy (Caller mode, no passphrase); the push's hand-written parser, its percent decoder and its port/latency constants are gone. The accepted set and the error text are unchanged (`fixtures/golden/srt/push-url-table.txt` matches without regeneration), and `SrtUrlOverrides` is replaced by `srt_runtime::SrtUrl` (`mode` and `passphrase` are now parsed as values rather than rejected by the parser).
- The push transports' wire bytes are pinned by `tests/it/push_wire_goldens.rs` (the RTMP `onMetaData`, sequence-header and first media bodies, and the `srt://` URL parse table), recorded before the code moved out of this crate (issue #2369).
- The RTSP pull plans its `SETUP` list and `PLAY` URI through `rtsp_runtime::PlayPlan` (control resolution, channel pairs, the RTP/RTCP collision check) instead of its own copy; a media control on another authority and an unsupported media are still errors, and relative controls now resolve against the DESCRIBE reply's `Content-Base` (else `Content-Location`, else the request URL kept with a trailing slash), per RFC 2326 Appendix C.1.1, so a `SETUP` that used to go to `rtsp://host/streamid=0` for a request URL `rtsp://host/test` now goes to `rtsp://host/test/streamid=0` (#2372). `PLAY` now goes to the SDP's session-level `a=control` when it names one.
- HLS pull retries resource fetches and honours `Retry-After` on 429/503.
- The WHIP and RTMP ingest loops share one admitted-session driver (`media_plane::ingress::AdmittedDriver`): acceptance, the per-session clock origin, the publish-then-reap sequence and the idle clock are one implementation instead of two copies. The WHIP loop's hand-written idle-clock map is gone (its gauge now reports the driver's live sessions), and the RTMP loop keeps only its own read future and protocol session.
- The RTMP ingest session's own `RtmpConnection` now drives rtmp-runtime's erased connection (`from_stream_erased`), so the golden tests replay the captured `rtmp/obs-publish.bin` publish through a real connection over an in-memory pipe (rtmp-runtime's `AsyncRtmpServer::accept` now returns the new `AcceptedRtmpConnection`).
- BREAKING: the Smooth pull source is an adapter over the new `smooth-runtime` engine (#2370). `SmoothAction`, `SmoothResourceId` and `StreamIdx` are replaced by `smooth_runtime::Action` and `SmoothInput`. It gains live-join look-ahead, discontinuity handling and the engine's retry/backoff (a failing fragment is retried with backoff, then skipped on a live presentation or ends a static one; a manifest failure is retried before ending the session). Timestamps are now placed at each fragment's `tfxd` start in the stream's own timescale; the old session restarted every fragment at 0 and declared video 90 kHz while its durations were in the manifest timescale. A `401` still ends the session at once.
- `FetchResult::NotReady`/`FetchOutcome::NotReady` are removed from the shared pull scheduler: nothing builds them now that the Smooth source's tolerated-404 loop is gone.
- The UDP-family ingest sources bind through `dvb_stream::udp::bind_standard`, the workspace's one UDP bind, instead of a crate-local `socket2` setup: same options (`SO_REUSEADDR`, `SO_REUSEPORT` where it exists, `SO_RCVBUF` with the 4 MiB default, the IPv4/IPv6 multicast join), and a refused `SO_RCVBUF` is still logged and the bind carried on.
- The raw RTP-over-UDP source reads the payload type through `rtp_packet::RtpPacket` rather than masking header byte 1, so the RTP header layout has one owner (a packet that is not a valid RTP header is dropped as before); that crate is now a plain dependency instead of being pulled in only by the `whep` feature.
- The 90 kHz clock rate is named once, from `broadcast_common::clock33::PTS_HZ`; `timed_metadata::PTS_HZ` (a re-export of the same constant) and a local copy are gone.
- The WHIP and WHEP endpoints build their SDP answer and ICE-restart answer fragment with `webrtc_runtime::sdp` instead of assembling the session here (#2363); the documents are byte-identical to before (goldens in `fixtures/golden/webrtc/`).
- The Smooth source and output use `broadcast-smooth`'s manifest model instead of `transmux`'s removed `smooth_parse` module (#2356); transmux keeps the fragments and the codec glue.
- The RTSP push sends RFC 2250 §2 MP2T packets built by `transmux::rtp::Mp2tPacketiser` and records through `rtsp_runtime::AsyncRtspClient::start_record`; multimux now supplies only the SDP media section and the 90 kHz timestamp (its one clock read). Its own RTP header writer, MP2T splitting, control-URL derivation and ANNOUNCE/SETUP/RECORD choreography are gone. The wire is byte-identical: `fixtures/golden/rtsp/push-wire.golden` records every request and interleaved packet from before the move and matches without regeneration (#2368).
- The RTSP push builds its ANNOUNCE session description with `rtsp_runtime::sdp::session_description` and supplies only its `m=` block, instead of assembling `v=`/`o=`/`s=`/`c=` itself; the body is byte-identical (`fixtures/golden/rtsp/rtsp-announce.sdp`).
- The DASH pull's `availabilityStartTime` reader parses through `dash_runtime::timing::datetime::parse_xs_datetime` instead of its own `jiff` call; the lexical UTC `Z` guard stays (#2371).
- The DASH-IF ingest reads the publisher's MPD and matches uploaded segment URLs with `dash-runtime` instead of transmux's removed MPD model (#2340).

An egress answer of `BadRequest` because a track cannot be described maps to a 5xx (`crate::http::into_response_with_message`).
- The monotonic-to-UTC anchor mapping (`HostClock` callers) comes from `broadcast_common::time::MonoUtc`; reading the host clocks stays in `clock.rs`.
- Timeline discontinuity detection now uses the per-track detector from `transmux` (broadcast-client semantics); the 10 s `MEDIA_DISCONTINUITY_NS` constant is removed.
- RTSP pull skips unplayable SDP media sections (and foreign-authority controls and sections beyond the track cap) instead of failing the whole route; fails only when nothing is playable. Skipped sections are logged as route warnings.
- The `hls-runtime` `tokio` feature is no longer enabled: `hls-runtime` no longer has one.

### Fixed
- DASH: after a reload (or source reconnect) with a byte-identical init, the MPD no longer lists the replaced route's unfinished segment number, which no origin serves and which answered `404` inside the time-shift buffer (ISO/IEC 23009-1 §5.3.9.5.3, `private/specs-verified/dash/23009-1/05-3-9-5-segment-information-derivation.md`; issue #2625). The replaced Period is early terminated with `@duration` at the end of its last finished segment (§5.3.2.1, `private/specs-verified/dash/23009-1/05-3-2-period.md`) and the replacement continues in the next Period from its first segment (`@start`, `startNumber`, `@presentationTimeOffset` as for an init change), per DASH-IF IOP 4.3 4.11.4.2 (`private/specs-verified/dash/dashif-iop-4.3/ch04-06-deployment-scenarios.md`). Because the init is unchanged the two Periods keep the same `AdaptationSet@id`/`Representation@id`, carry an equivalent `AssetIdentifier` (a private scheme, IOP 5.5.1) and the new Adaptation Set signals `urn:mpeg:dash:period-connectivity:2015` with the earlier Period's `@id` while that Period is listed (§5.3.2.4; not period-continuity, since the skipped segment leaves the timestamps non-continuous; DVB-DASH players bridge the gap per ETSI TS 103 285 §10.5.2.4). A reload that skips no number keeps one Period, and an init change behaves as before.
- DASH: a reload (or source reconnect) whose new init segment differs from the replaced one now opens a new Period at the first new segment instead of listing the new codec under the old Period (ISO/IEC 23009-1 §5.3.2, `private/specs-verified/dash/23009-1/05-3-2-period.md`; issue #2611). The new Period has its own `@id`, `@start` at that segment's MPD start (so the replaced Period ends there), `startNumber` at its number and `@presentationTimeOffset` at its media start. The replaced Period stays listed, closed with `@duration` at the end of its last segment, and its segments and init segment keep being served from the retained replaced program while they are inside the time-shift buffer (§5.3.9.5.3); the Period, and the replaced program, go once its last segment leaves the window. A byte-identical init keeps the replaced Period and init generation unchanged. No period-continuity/connectivity descriptor or `AssetIdentifier` is written (an init change rules out both, §5.3.2.4).
- DASH: a Period's `@id`, `@start`, `startNumber` and `@presentationTimeOffset` are fixed when it opens and no longer change as the window slides past its first segment (§5.4.1 keeps `Period@id` across MPD updates); before, they were taken from the window's front and renumbered. Every Period after the first now carries `@presentationTimeOffset`, which was missing, so its first segment presented `@start` too late (`fixtures/golden/hls/track-gap-live.golden` gains the attribute).
- A replacement of a changed route continues the replaced route's timeline: its first segment carries `EXT-X-DISCONTINUITY`, `EXT-X-DISCONTINUITY-SEQUENCE` carries on from the old playlist, and the DASH manifest keeps the old `availabilityStartTime` and `startNumber` (a restore after a failed reload does the same).
- An LL-HLS blocking-reload request (or any GET/HEAD) being served by a route that an admin reload replaces or an admin removal deletes is no longer left to time out with a `503`: the admin media service drops it as soon as the route is retired and serves it again against the router that is live then, so it keeps waiting for the same `_HLS_msn`/`_HLS_part` on the replacement, or answers `404` when no route of that name is left. A replacement of a changed route now numbers its media sequence above what the old route had shown (as well as above the archive), so a client's `_HLS_msn` keeps its meaning across the reload (#2593).
- A reload no longer installs over a runtime a concurrent admin add registered while the reload waited for its locks (every runtime carries a generation and the re-plan compares them, not just the touched names), which used to leave the replaced runtime running undrained. A reload that restarts a changed route now drains the old runtime before reading the route's archive floor and spawning the replacement, so the new runtime cannot number below a segment the old one still writes; if a later step of the reload fails, the stopped routes are started again from their old configuration (#2578, #2579).
- The session host dropped a pending session timer when an earlier timer fired in the same step (it kept only the soonest wake-up), so a pull could sit idle until its read timeout, most visibly after a conditional MPD refresh answered `304`. It now keeps every requested wake-up.
- A WHIP session's idle bound is measured from the last datagram that carried media: the driver's activity flag was never set, so the deadline stayed at admission plus the read timeout whatever the publisher sent.
- DASH pull runs the relay `broadcast_client::Session` through the shared session host: the session owns the MPD, Period and AdaptationSet selection, addressing, the UTC clock ladder, live-edge joining, availability gating, conditional MPD refresh, failure classification and retry; the host performs the HTTP requests, anchors the session's wall clock to the host clock (re-read every `utc_resync_us`) and stitches the sample timeline across Period boundaries. The route's cross-origin opt-in is `DashConfig::cross_origin_urls`. A presentation the session cannot play (no playable Representation, an unusable first MPD) fails the attempt as the typed `MultimuxError::Session`.
- Each admitted RTMP session reads on its own task, which owns the connection (the `Arc<Mutex<RtmpConnection>>` is gone) and hands its outcomes to the route's publisher over a bounded channel, so a publisher busy segmenting no longer stops other sessions' reads (issue #2525). WHIP still polls its sessions' reads from one task.
- Catch-up keeps its period-index cache and its scan permits (4 concurrent scans) per route instead of process-wide, so one route's slow archive no longer starves another's viewers (issue #2528).
- DASH-IF ingest holds at most 64 MiB of buffered non-segment objects per route at once (`DashifIngestRoute::with_buffered_budget_bytes`); a request over the budget answers `503` with `Retry-After`. A buffered non-segment object is capped at 8 MiB (`with_max_buffered_object_bytes`), below the 64 MiB cap that still applies to a streamed segment (issue #2532).
- A blocking-reload request that wakes on a cold egress (`ServedEgress::is_warm` false: the first Smooth plan, the I-frame and bitrate scans of a new HLS segment) runs `prepare` on the blocking pool, at most eight at a time, instead of on the waking worker (#2538).
- HLS media and I-frame playlists and DASH/LL-DASH MPDs are rendered once per state stamp and shared by concurrent requests (#2526).
- HLS pull runs the relay `broadcast_client::Session` through the shared session host: the session owns playlist reload and Low-Latency blocking reload, preload-hint prefetch, AES-128 keys, fMP4 and classic-TS demux, per-resource retry with backoff (eight attempts, 0.5 s doubling to 30 s), `Retry-After`, redirects, cookies and auth; the host performs the HTTP requests. A finite playlist still ends the pull cleanly and the route is served as ended; a `401`/`403` on a resource or key still fails the attempt at once. Fatal and permanent session errors (undecryptable or unsupported content) surface as the new typed `MultimuxError::Session`.
- The Smooth output keeps one `SmoothOrigin` per program, so its cached plan and packaged fragments survive between requests, and hands it the segments as shared `Bytes` instead of copying every window segment per request. A request that misses the cache builds on the blocking pool (`spawn_blocking`, at most four at once per program); the module doc that claimed `http::resolve_blocking` did so was wrong (issue #2522).
- A Smooth fragment request the origin's window does not hold answers `404`, as an evicted HLS segment does, instead of `500`: the Smooth fallback passed its server-error status as the not-found status too, so every `EgressResponse::NotFound` from the origin (a start time before the window or past its end) became an internal error (issue #2506).
- An HTTP pull (HLS, DASH, Smooth, TS-over-HTTP) keeps the auth state for the whole session: a cookie an origin sets on the playlist is sent with the segments, and a Digest challenge is negotiated once instead of on every request, because the state is updated in place rather than cloned per request. Cookies are stamped with the pull's own clock instead of `0`.
- A `407` from an HTTP pull is returned unchanged instead of being retried; there is no proxy-credential configuration, and the origin's credentials are never sent as a proxy's.
- The challenge-answer flag a pull passes on reports whether the request really carried an `Authorization` header, so a Digest state that has not negotiated its first nonce is not treated as a rejected credential.
- `rebuild_index` now walks fMP4 boxes through `transmux::parse_box`, so segments whose `mdat` uses a 64-bit `largesize` (or whose last box runs to EOF) are indexed completely.
- The segment pump and push outputs treat the new `SampleCursorItem::TracksLagged` like a `TracksChanged` to the carried track set (audit A11-2).
- A route advertises what is being served (audit A11-1): its track specs (DASH `codecs`, HLS master `CODECS`) are set only after the segmenter accepts a track change, so a refused change no longer leaves the route naming codecs the segmenter is not producing. The specs of each init generation are kept, so segments still in the DVR window keep the specs they were cut under.
- A track set the container cannot mux (empty, or data only) is an explicit gap state of the segmenter instead of a refused codec change: the current segment is closed at the boundary, one gap placeholder segment (target duration, no media) is published, and samples are dropped until a muxable set arrives, which resumes with `EXT-X-DISCONTINUITY` and a rebuilt segmenter that continues the segment numbering. HLS playlists carry `EXT-X-GAP` (RFC 8216bis §4.4.4.7) for the placeholder; the placeholder is one target duration however long the source stays empty.
- The DASH MPD splits into Periods at a gap: the Period ends where the placeholder begins (`Period@duration`) and the next one starts at its first segment's number with the track set that segment was cut under. A window holding nothing but gap placeholders answers 503. A later Period still names the bare `init-$RepresentationID$.mp4`, which the resource route serves as the current init.
- A route's track specs (what the DASH and LL-DASH manifests derive `codecs` from) follow the in-band `SampleCursorItem::TracksChanged` the segment pump reads, and are seeded from the segmenter's start snapshot, instead of being synced from `Trunk::track_generation` ahead of the samples still queued under the previous set (audit A10-7).
- The RTSP pull warns again when a Sender Report rejection of the same kind recurs after the reports recovered: an RTCP frame that is neither rejected nor skew-refused clears the remembered rejection (audit A10-6).
- A track change the segmenter cannot apply (no fMP4-muxable track, or a failed rebuild) leaves the published track set and timescale moves at the ones the installed segmenter carries, instead of routing later samples by a set its muxer rejects (audit A10-5).
- Push outputs (RTMP/SRT/RTSP) renegotiate their track selection on the in-band `SampleCursorItem::TracksChanged`, after every sample published under the previous set has been sent, instead of comparing `Trunk::track_generation` before draining the cursor (audit A10-1).
- `ProgramSegmenter::try_new` takes its cursor, track generation and track set in one `Trunk` call, so a concurrent `set_tracks` can no longer leave its marker ignored (audit A10-3). An fMP4 rebuild starts the new init generation at the segment after the last one flushed or still queued, not the trunk's last closed segment, so a stalled DVR pin no longer moves the init (and the HLS discontinuity) onto an earlier segment (audit A10-2).
- `ProgramSegmenter` switches track set on the in-band `SampleCursorItem::TracksChanged` rather than by comparing `Trunk::track_generation` before draining, so samples published before a Smooth quality switch are never muxed under the new init (audit A9-4).
- An fMP4 rebuild after a track change gates only video until the new level's first sync sample; audio no longer dropped for that interval (audit A9-3).
- The RTSP pull warns about rejected Sender Reports only when the rejection starts or its reason changes, and logs the rest at debug, instead of one warning per Sender Report (audit A9-5).
- The Smooth pull forwards the engine's `Output::TracksChanged` as `SessionEvent::TracksChanged` so the trunk's track set follows a quality switch.
- The RTSP pull logs (warn) each Sender Report it ignored for NTP time zero and each set refused for tracks more than an hour apart; a repeated timeline-step discontinuity warns once and the repeats log at debug instead of flooding, and `queue_placed` no longer returns a count only a test read (the tests assert the log output).
- The RTSP pull logs (warn) the aligner's timeline-step `Discontinuity` and placement-rule `State` outputs instead of dropping them silently; `media_plane::SessionEvent` has no equivalent to forward.
- The Smooth pull keeps logging the engine's `Output::Discontinuity` rather than forwarding it: `media_plane::SessionEvent` has no discontinuity event, so unlike `broadcast-client` (`Event::Discontinuity`) the trunk gets no marker; pinned by a unit test.
- Every pull honours the server's `Retry-After` (RFC 9110 §10.2.3) on a `429`/`503`, not only HLS resource fetches: an HLS playlist fetch is retried after the wait instead of ending the session, a DASH retry waits the longer of its backoff and the server's wait, and a Smooth retry passes the wait to `smooth-runtime` (#2393).
- An RTSP pull reads the SETUP reply's transport with `take_negotiated_transport()`, so a track whose reply has no `Transport` header fails with a SETUP protocol error instead of inheriting the previous track's channels.
- An RTSP pull routes interleaved media by the RTP channel the server negotiated for each track, so a server answering `interleaved=1-2` no longer has every frame dropped as an odd channel.
- `rescale_to_90k` now wraps the rescaled RTP timestamp into the 32-bit range explicitly (RFC 3550 §5.1) instead of relying on `as u32`.
- `Recorder::lines` and `Recorder::len` recover a poisoned lock via `PoisonError::into_inner` instead of returning an empty golden.
