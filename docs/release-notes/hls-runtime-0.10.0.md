# hls-runtime 0.10.0

_Released 2026-10-31._

### Changed (BREAKING: epoch)
- Builds against new caret epochs of workspace siblings (`broadcast-hls` 0.4 -> 0.5, `transmux` 0.27 -> 0.28, `timed-metadata` 0.7 -> 0.8, `media-plane` 0.7 -> 0.8, `container-probe` 0.2 -> 0.2.1 (minimum: segment-structure checks moved here)). A caret-epoch change is major-class for a 0.x crate under the epoch-purity rule (`docs/RELEASE-AUDIT.md` section 2), whatever its own API diff, so this release is a minor bump; consumers must resolve a single copy of each of those crates.
### Breaking
- Removed the `HlsSkip`/`HlsSkipDirective`/`SkipValue` type aliases and `HlsOrigin::priority`/`urgency_for` methods; use `SkipDirective` and `HlsOrigin::http_priority` instead. `HttpPriority` now keeps a single `SEGMENT` constant for parts and segments.
- A response the core rejects no longer ends the session: it is counted in `TokioClientStats::rejected_responses`, exposed as `TokioClient::last_rejection()` and retried with backoff; sixteen rounds in a row without output end it. New `TokioClientConfig::max_body_bytes` (default 256 MiB, `with_max_body_bytes`) bounds every body; `TokioError::BodyTooLarge` (not retried). **Breaking for struct-literal construction:** `TokioClientConfig` and `TokioClientStats` gained a field.
- `HlsOriginBuilder::declared_bandwidth_bps(u64)` — operator-declared peak bitrate used as a floor for the master playlist `BANDWIDTH` before any segment with a measurable duration exists (and afterwards); validated `> 0` and `<= u32::MAX` at build (`HlsOriginBuildError::InvalidDeclaredBandwidth`). `HlsOrigin::master_playlist` now returns `HlsMasterError::BandwidthUnknown` when neither a measured segment nor a declared value is available instead of advertising a 5 Mb/s placeholder. `master_playlist_m3u8` now takes `bandwidth_bps: u32`.
- `PLACEHOLDER_BANDWIDTH_BPS` constant.

### Added
- `FRAME-RATE` on every video variant of an fMP4 origin whose SPS carries no VUI timing (Apple HLS authoring spec item 9.15): measured from the drained segments as video samples over summed `trun` duration, in the video track's timescale. A VUI-signalled rate still wins.
- Dolby Vision multivariant signalling (issue #1428): a single-layer HEVC Dolby Vision track gets `CODECS` plus `SUPPLEMENTAL-CODECS` and `VIDEO-RANGE` per the Apple HLS authoring spec: profile 8.1 `hvc1...` + `dvh1.08.LL/db1p` + PQ, profile 8.4 `hvc1...` + `dvh1.08.LL/db4h` + HLG, profile 5 `dvh1.05.LL` + PQ. Other compatibility ids are not signalled.
- HDR10+ multivariant signalling (issue #1428): an HEVC PQ track whose `TrackSpec::hdr10plus` is set gets `SUPPLEMENTAL-CODECS="<codec>/cdm4"` next to `VIDEO-RANGE=PQ`. Apple prints the `cdm4` brand only for AV1; the HEVC form is an inference from the same rule. A Dolby Vision track keeps its own `SUPPLEMENTAL-CODECS`. The flag survives `set_init` re-deriving specs from the init segment.
- `HlsOrigin::set_part_target_ms` raises one origin's `EXT-X-PART-INF` `PART-TARGET` above the configured value, for a rendition whose frames do not divide it (an audio rendition needs a whole number of frames). `PART-HOLD-BACK` on every playlist of a presentation is now three times the largest `PART-TARGET` among the origin and its rendition siblings, so `EXT-X-SERVER-CONTROL` stays identical across playlists (RFC 8216bis sections 4.4.3.8 and 6.2.4; issue #1603).
- A low-latency `Container::WebVtt` origin now serves Partial Segments like the other containers (issue #1592): its media playlist renders `EXT-X-PART-INF`, `EXT-X-PART` and `EXT-X-PRELOAD-HINT`, `part-*.vtt` resources resolve and wait for a part that is about to be published, and a blocking reload with `_HLS_msn` and `_HLS_part` waits for the requested part exactly as it does for fMP4. This replaces the interim behaviour that rendered `EXT-X-PART-INF` without parts and mapped `_HLS_part` to part 0 of the next segment.
- `HlsOrigin::set_subtitle_renditions` replaces the declared WebVTT subtitle renditions after construction, for a host that learns them from the stream (issue #1428); validated like the builder's, previous declarations kept on error.
- WebVTT subtitle renditions (issue #1428): `Container::WebVtt` serves `.vtt` segments with no `EXT-X-MAP`; with `low_latency` it also serves Partial Segments (see the #1592 entry), `EXT-X-SERVER-CONTROL` and rendition reports (RFC 8216bis Appendix B.1). `SubtitleRenditionDecl` + `HlsOriginBuilder::subtitle_renditions` add one `EXT-X-MEDIA TYPE=SUBTITLES` per declaration in group `SUBTITLES_GROUP_ID` (`"subs"`), set `SUBTITLES="subs"` on every `EXT-X-STREAM-INF` and append `wvtt` to a known `CODECS` (Apple authoring 5.10). `hearing_impaired` emits the Apple 4.5 `CHARACTERISTICS` and forces `AUTOSELECT=YES` (4.6); `forced` emits `FORCED=YES` and forces `AUTOSELECT=YES` (5.11); `LANGUAGE` is required (4.7). `validate_subtitle_renditions` and new `HlsOriginBuildError` variants reject empty name/language/uri, duplicate NAME or URI, `DEFAULT=YES` without `AUTOSELECT=YES` and more than one `DEFAULT=YES`. `HlsOriginBuilder::subtitle_sibling_origins` checks each sibling is a WebVtt origin with the primary's `EXT-X-TARGETDURATION` (Apple 5.6). Without declarations the master is unchanged.
- `Container` gained the `WebVtt` variant. `Container` is `#[non_exhaustive]`, so this is not a breaking change for downstream matches.
- Closed-caption signalling (issue #1428): `HlsOrigin::set_detected_closed_captions` records the caption streams the video carries; the master playlist then lists one `EXT-X-MEDIA TYPE=CLOSED-CAPTIONS` per stream in group `CLOSED_CAPTIONS_GROUP_ID` (`"cc"`, `NAME` = the `INSTREAM-ID`, no `URI`, `DEFAULT=NO`, `AUTOSELECT=NO`) and every `EXT-X-STREAM-INF` carries `CLOSED-CAPTIONS="cc"`, replacing `NONE` when `closed_captions_none` is set. Until a stream is recorded the master is unchanged. `ClosedCaptionDecl` + `HlsOriginBuilder::closed_caption_overrides` set `NAME`/`LANGUAGE` per `INSTREAM-ID` (validated by `validate_closed_caption_overrides`; new `HlsOriginBuildError::{InvalidClosedCaptionInstreamId, DuplicateClosedCaptionInstreamId}`). `LANGUAGE` is omitted unless configured: the bitstream has none and Apple's `mediastreamvalidator` flags a placeholder `und`.
- Split-audio rendition reports (issue #1428 slice 4): every LL media playlist of a split route now emits one `#EXT-X-RENDITION-REPORT` per other rendition (video and each audio), with `LAST-MSN`/`LAST-PART` snapshotted from that sibling's own live edge at render time. The I-frame playlist keeps its existing media report and gains the audio siblings' reports. Non-split routes render byte-identically.
- Split-audio multivariant playlists (issue #1428 slice 3): `HlsOriginBuilder::audio_sibling_origins` folds the sibling audio origins into the primary origin's master. Each audio group's `EXT-X-STREAM-INF` carries `CODECS` = video codec plus the group's distinct audio codecs (RFC 6381 strings from the tracks' `TrackSpec`), `BANDWIDTH` = video peak plus the group's largest audio peak, and `AVERAGE-BANDWIDTH` likewise over averages (Apple authoring items 9.13/9.14). `declared_bandwidth_bps` floors the video part only. `LANGUAGE` (BCP 47 language tag derived from the PMT ISO 639-2 code via
`bcp47_language`, mapping ISO 639-2/B and 639-2/T to ISO 639-1 when one
exists), `NAME` (unique within the group, ` (AD)` suffix for audio description), `CHARACTERISTICS` (`public.accessibility.describes-video` for audio description) and `CHANNELS` are derived from `TrackSpec::audio_metadata()` and the codec config when the declaration leaves them empty; declared values always win. `validate_audio_renditions_relaxed` accepts such declarations. Routes without siblings render byte-identically.
- `validate_audio_renditions` is now public (issue #1428 slice 2b) so hosts can validate declarations at config time. A segment published with no media bytes now renders as `EXT-X-GAP` (it occupies its media sequence number without media).
- Multivariant playlists can declare separate audio renditions: `HlsOriginBuilder::audio_renditions(Vec<AudioRenditionDecl>)` emits one `#EXT-X-MEDIA:TYPE=AUDIO` per declaration before the variants and sets `Variant.audio` per referenced group; `HlsOriginBuilder::closed_captions_none(bool)` emits `CLOSED-CAPTIONS=NONE`. Default (no declarations) keeps the previous byte-identical output. Typed `HlsOriginBuildError` variants validate the declarations at `build()` (non-empty group/name/language/uri, unique NAME per group, exactly one DEFAULT=YES per group and DEFAULT implies AUTOSELECT, identical members across groups); a URI equal to the media playlist name is `HlsMasterError::AudioRenditionUriEqualsMediaPlaylist` at render time.
- I-frame (trick-play) playlists now carry LL-HLS directives: `EXT-X-PART-INF` (PART-TARGET), `EXT-X-SERVER-CONTROL` (CAN-BLOCK-RELOAD, PART-HOLD-BACK, HOLD-BACK, CAN-SKIP-UNTIL, CAN-SKIP-DATERANGES), and an `EXT-X-RENDITION-REPORT` pointing back at the primary media playlist (RFC 8216bis §4.4.5.4 SHOULD). Apple's `mediastreamvalidator` no longer reports the PART-INF/server-control findings against the live origin for the I-frame variant.
- Playlist Delta Updates (RFC 8216bis §6.2.5.1): `BlockingQuery` now carries a typed `_HLS_skip` directive (`SkipDirective::Yes`/`V2`) and the origin renders an `EXT-X-SKIP` delta update (omitting segments older than the Skip Boundary, `MEDIA-SEQUENCE` unchanged) when `CAN-SKIP-UNTIL` is advertised; ignored otherwise. With `YES` every `EXT-X-DATERANGE` tag stays; `v2` also omits older dateranges and reports them via `RECENTLY-REMOVED-DATERANGES`. The origin now advertises `CAN-SKIP-UNTIL` (6x Target Duration) and `CAN-SKIP-DATERANGES=YES`. `_HLS_primary` is accepted and carried opaquely. `HlsOrigin::http_priority` exposes the RFC 9218 urgency for a request (playlist=1, part/segment=2). `_HLS_skip` is ignored when the playlist has no `CAN-SKIP-UNTIL` or carries `EXT-X-ENDLIST` (this origin never emits ENDLIST).
- `Error::NotMedia { id }` (additive; `Error` is `#[non_exhaustive]`): a Part/Segment body that is not media for its container is rejected by `on_resource` instead of being consumed silently. MPEG-TS needs the sync byte on at least half of its 188-byte lanes (ISO/IEC 13818-1 §2.4.3.2), ISO BMFF a complete `moof` then `mdat` (ISO/IEC 14496-12 §8.8.4) or a progressive movie (still `Error::NotFragmented`). Structurally valid media with zero samples is still accepted. A non-`0x47` body used to be buffered forever as "waiting for an init" a TS playlist never has, ending a VOD cleanly with samples missing.
- `HlsClient::retry_resource(id)`: re-request a failed Part/Segment with its original URL and byte range without a playlist reload, for a VOD playlist (`EXT-X-ENDLIST`) that has no reload to do it.
- `HlsClient::skip_resource(id)`: give up on a Part/Segment: it is never requested again, the TS timeline restarts (the old timeline's held-back access units are flushed first) and `Output::Discontinuity` follows; a skip of the last open segment of an ended playlist ends the stream.
- `Error::InitUndecodable` (additive; `Error` is `#[non_exhaustive]`): a fetched Media Initialization Section with no complete `moov` box was accepted and only failed later as an endless series of segment demux errors. It is now rejected at once, the slot is marked failed, and `retry_init()` fetches it again.
- `Output::TrackSkipped { track_id, fourcc, reason }` (additive; `Output` is `#[non_exhaustive]`): a track of an fMP4 init the demuxer could not model (an encrypted `encv`/`enca` sample entry, an unrecognised codec) was dropped silently although `Media::skipped` named it. Emitted once per track and init; a stream whose every track is skipped still produces an empty `Output::Tracks`.
- `Output::FragmentDamaged { id, skipped }`: `moof` fragments of a Part/Segment the demuxer had to skip (`Media::degraded`), notably those whose sample data offset points outside the resource (absolute `tfhd` base-data-offset). The samples of the intact fragments are still emitted.
- `Error::NotFragmented { id }`: a segment of an fMP4 playlist that is a progressive movie (`moov`, no `moof`) used to demux to zero samples without an error.
- `Output::TrackDropped { track_id, stream_type }` (additive; `Output` is `#[non_exhaustive]`): a TS-segment elementary stream that cannot be carried in fragmented MP4 (`!is_muxable_in_bmff`, e.g. SCTE-35/ID3/private data) is no longer dropped silently. Emitted each time the demuxer announces the track; a consumer reporting it deduplicates by `track_id`.
- `HlsClient::set_playlist_base(url)`: the URL relative playlist, segment, key and map URIs resolve against (the final URL of a playlist response after redirects, RFC 3986 section 5.1.3). Reloads keep requesting `playlist_url()`; the base is cleared when the client switches playlist.
- `HlsClient::endlist_seen()` and `HlsClient::target_duration_secs()`: read-only accessors for the playlist's VOD/live state and `EXT-X-TARGETDURATION` (broadcast-client playout gate, issue #1455).
- HLS `METHOD=AES-128` decryption in `HlsClient` (issue #1459, slice S1): new `Action::FetchKey { id, url }`, `KeyId`, `HlsClient::on_key` / `on_key_error`. Keys are fetched once per URI, segments are held until the key arrives, then decrypted (IV attribute or big-endian Media Sequence Number) before demuxing. New errors `BadKeyLength`, `UnrequestedKey`, `DecryptFailed` and `UnsupportedEncryption` (SAMPLE-AES and other methods, encrypted `EXT-X-MAP`, I-frames-only, partial segments). The `tokio` adapter fetches keys itself. Depends on `transmux` with the `sample-aes` feature.
- `HlsClient` now accepts a master (multivariant) playlist URL: `on_playlist` detects `#EXT-X-STREAM-INF`, parses `broadcast_hls::MasterPlaylist`, emits `Output::Master(MasterSelection)`, and follows the selected variant. New types `VariantPolicy`, `VariantInfo`, `RenditionInfo`, `MasterSelection`; `set_variant_policy` and `select_variant` for policy-driven and manual variant switching. Audio/subtitle renditions with a URL are exposed (not fetched) for a second client.
- `HlsOrigin::render_playlist` now derives `#EXT-X-PROGRAM-DATE-TIME` for closed and open segments from the trunk time anchor plus `Trunk::segment_start_time` (Apple authoring 8.4); emits nothing when the anchor or a segment start is unknown. Live and I-frame playlists now always emit `#EXT-X-DISCONTINUITY-SEQUENCE` (including `:0`) (Apple authoring 8.17).
- `HlsOrigin` now computes, stores and renders an I-frame trick-play playlist: `HlsRequest::IFramePlaylist { track_id, query }`, `HlsOrigin::iframe_playlist_name(track_id)`, and `HlsOrigin::render_iframe_playlist` produce an `#EXT-X-I-FRAMES-ONLY` media playlist with `BYTERANGE=len@0` per entry, derived from the first video sample of each segment (sync sample starting at the mdat payload start).
- `HlsOrigin`'s master playlist now carries `FRAME-RATE` (Apple HLS Authoring Specification item 9.15; RFC 8216bis §4.4.6.2) as the maximum nominal frame rate across all video tracks, derived solely from an SPS's VUI timing via `transmux::nominal_frame_rate_millihertz` (H.264 and HEVC; HEVC uses the HRD fixed-pic-rate tier when present, else the ClockTick convention). Codecs without VUI timing omit it (never invented); audio-only origins omit it; a new init clears it.
- `HlsOrigin` now derives and advertises `VIDEO-RANGE` (`HLG`/`PQ` only; SDR/unknown omitted) in the master playlist from the first video track's display colour description (RFC 8216bis §4.4.6.2).
- `HlsOrigin` now derives and advertises `RESOLUTION` in the master playlist from the first video track (AVC/HEVC) display geometry: square-pixel presentation size (cropped output, rescaled by SAR), via `transmux::presentation_size`. Audio-only origins omit it.
- `HlsOrigin`'s master playlist now carries `AVERAGE-BANDWIDTH` (Apple HLS Authoring Specification item 9.14; RFC 8216bis §4.4.6.2): the mean segment bitrate over every segment the origin has drained, `round(sum(bytes) * 8 / sum(seconds))`, surviving playlist-window eviction. It is clamped to `BANDWIDTH` (a mean can never exceed the peak) and omitted, never invented, until a segment with a measurable duration has closed. Requires `broadcast-hls`'s new typed `Variant::average_bandwidth`.
- `HlsClient` now emits `Output::Tracks(Vec<transmux::TrackSpec>)` (the full current track set) and `Output::DisplayChanged { track_id, pts, display }` (from `DemuxEvent::DisplayChanged`). TS path emits `Tracks` immediately before every re-synthesized `Init`; fMP4 path emits `Tracks` once after the first `Init` and again only when a new `Init` yields a different spec set. `DisplayChanged` flushes the affected track's pending samples first so output order matches sample order.

### Changed
- I-frame playlist `EXT-X-RENDITION-REPORT` now uses the real configured media playlist name instead of the hardcoded `"media.m3u8"`; threaded through `HlsRequest::IFramePlaylist::media_playlist_name` (adapter supplies `LlHlsState::playlist_name`).
- Master playlist `BANDWIDTH` is never fabricated: `HlsOrigin::master_playlist` keeps returning `HlsMasterError::BandwidthUnknown` (hosts map to HTTP 503 with `Retry-After`) until a segment with a measurable duration has been drained or `HlsOriginBuilder::declared_bandwidth_bps` is set; once measured it ratchets up only and never drops on a later smaller segment.
- `EXT-X-TARGETDURATION` is now frozen at the first render that has at least one segment in the window (RFC 8216 §4.3.3.1): once published it never changes; longer later segments are counted, not re-advertised. Previously it tracked the running maximum and could move between playlist versions.
- The structural "is this body media" checks behind `Error::NotMedia` (TS lane lattice, `moof`+`mdat`, progressive `moov`) are now `container-probe::segment::{ts_structure, media_fragment, progressive_movie}` instead of private functions; behaviour is unchanged. New dependency on `container-probe` 0.2 (`no_std`+`alloc`).
- I-frame (trick-play) playlist segment URIs now use the `iframe-seg-{track}-{instance}-{seq}.m4s` prefix instead of `seg-…` (issue #1422). The bytes behind an I-frame URI are always the stored segment bytes, so the advertised `#EXT-X-BYTERANGE` length (measured on the stored bytes) can never drift under DASH `emsg` splicing. `parse_immediate` resolves `iframe-seg-…` to the same `ImmediateResource::Segment` (immutable when instance-named). `seg-…` names are unchanged.

### Fixed
- `EXT-X-TARGETDURATION`, and with it `HOLD-BACK` and `CAN-SKIP-UNTIL`, now follows the largest target duration across an origin's sibling renditions, so every Media Playlist of a route carries the same `EXT-X-SERVER-CONTROL` attributes and values (RFC 8216bis section 6.2.4, Apple HLS authoring spec 5.6). Each playlist used to derive them from its own segments, so an audio rendition with shorter segments advertised `HOLD-BACK=12` next to the video's `33` (issue #1621).
- `FRAME-RATE` is now also emitted for MPEG-TS-container (TS-HLS) variants whose video carries no VUI timing, e.g. iPhone camera originals (issue #1614; Apple HLS authoring spec item 9.15, RFC 8216bis section 4.4.6.2). It is measured per drained segment from the demuxed video samples' DTS deltas (unwrapped through `broadcast_common::clock33`), and the origin reports the highest per-segment mean rate over the segments currently in the playlist window, so a variable-rate stream reports its maximum rather than its overall mean and a segment with broken timestamps ages out when it leaves the window. A segment with fewer than two samples or zero measured duration is ignored. The same maximum rule now applies to fMP4 origins; constant-rate output is unchanged.
- An I-frame playlist request carrying both `_HLS_msn` and `_HLS_part` now waits on the Media Sequence Number and is served, instead of answering 400. RFC 8216bis section 6.2.5.2 makes only `_HLS_part` without `_HLS_msn` a Bad Request; Apple's `mediastreamvalidator` sends `_HLS_msn=M&_HLS_part=N` to the I-frame playlist of a low-latency route (issue #1594 investigation).
- A playlist served from a subdirectory (a split-audio rendition at `audio/a0.m3u8`) now references the init, segment and part resources, which sit at the stream root, as `../name`. Its bare names resolved to `audio/name`, which nothing serves, so a client following RFC 3986 could not load a single audio resource (issue #1599; Apple `mediastreamvalidator` reported it as 'Media file does not exist').
- The `EXT-X-RENDITION-REPORT` an I-frame playlist carries for its media playlist now reports the media playlist's own live edge, with `LAST-PART` when the media playlist has Partial Segments and `LAST-MSN` of the last Partial Segment (RFC 8216bis section 4.4.5.4: `LAST-PART` is required if the Rendition contains a Partial Segment). It reported the last closed segment with no `LAST-PART`. A media playlist still carries no report for the I-frame playlist: Appendix B.1 makes that a SHOULD, Apple's validator rejects it as "Unknown rendition report", and on a route with one media playlist its finding "No rendition reports in low-latency playlist" has no spec-conforming remedy (issue #1595).
- A low-latency media playlist now renders `EXT-X-PRELOAD-HINT` for part 0 of the next Media Sequence Number in the moment after a segment closes and before its successor has a part (issue #1577). RFC 8216bis Appendix B.1: a Playlist that contains an `EXT-X-PART` tag but no `EXT-X-ENDLIST` tag also contains an `EXT-X-PRELOAD-HINT` for the next Partial Segment. The hinted resource blocks until produced, as other hinted parts do.
- A low-latency WebVTT origin now renders the same `EXT-X-SERVER-CONTROL` attributes and values as a primary origin with the same low-latency configuration (`CAN-BLOCK-RELOAD`, `PART-HOLD-BACK`, `HOLD-BACK`, `CAN-SKIP-UNTIL`, `CAN-SKIP-DATERANGES`), as RFC 8216bis section 6.2.4 requires of every Media Playlist in a presentation (issue #1589). Because it advertises `CAN-SKIP-UNTIL`, it now answers `_HLS_skip` with an `EXT-X-SKIP` delta update.
- **An `EXT-X-MAP` whose URI query changes on every reload is the same init.** The init identity was the full resolved URL, so a CDN that re-signs the map URI (as it re-signs segment URIs, whose continuity already ignores the query) made the client refetch the init on every playlist reload and re-announce `Output::Tracks` each time. The identity is now the resolved URL without its query plus the `BYTERANGE`; a different path or byte range is still a new init. The slot keeps the newest URI (and its fresh token) for any later fetch or `retry_init()`.
- **Every segment is demuxed with the init of its own `EXT-X-MAP` run** (RFC 8216 §4.4.4.5: a map applies to every following segment until the next map). The client used to plan one init from the playlist's *last* map, so a VOD (or a join window) with a mid-roll init change never fetched the first init and decoded the earlier segments with the wrong one (50 H.264 samples read as HEVC, the audio lost). It now keeps one init per map-run, binds each Media Sequence Number to the init that precedes it, fetches each init once, and replays segments that arrive before their init once it is in. Behaviour changes: inits are fetched **one at a time**, in playlist order (`ResourceId::Init` names the one in flight, so a second concurrent fetch could not be told apart); the first init is announced as `Output::Init` as soon as it arrives, every later init (and a return to an earlier one) is announced lazily, immediately before the first resource demuxed with it and after that resource's `Output::Discontinuity`, followed by the matching `Output::Tracks`; `retry_init()` retries every failed init; the map key of each run is the `EXT-X-KEY` preceding that `EXT-X-MAP` line (an unusable encrypted map skips only the segments of its run). Held inits no segment still being fetched refers to are pruned, the newest is kept.
- Live TS-HLS (no `EXT-X-ENDLIST`) now starts emitting once a media segment has been fully fed: a PID the PMT declares that sent nothing in the segment no longer holds its program back until an `ENDLIST` that a live playlist never has (`StreamingTsDemux::release_silent_heads` after every whole segment; parts are not segment ends).
- `EXT-X-DISCONTINUITY` on a TS playlist restarts the demuxer's timeline (`StreamingTsDemux::restart_timeline`) instead of discarding the demuxer: the track set and track ids are kept, so a PID whose parameter sets are not in the new timeline's first segment (a segment that opens mid-GOP) is no longer lost, and no `Tracks`/init is re-announced for an unchanged track set. The old timeline's final access units are still flushed before `Output::Discontinuity`, and the segment that straddles the seam loses at most its in-flight PES per PID.
- A TS segment carrying an opaque PES data track (e.g. `stream_type` 0x06 private data) made the synthesized init fail with `UnmuxableDataTrack`, so every segment was rejected and a live playlist retried forever with no `Tracks`/`Samples`. Tracks `build_init_segment` cannot carry (`!is_muxable_in_bmff`) are now left out of the track set, the synthesized init and the emitted samples.
- A query string that differs between two windows is a re-signing (not an origin restart) only when it differs on every shared segment; a window where some shared segments keep their query and others change it is an origin restart (`Output::Discontinuity`).
- `EXT-X-SKIP` delta reloads: the merged playlist (skip cleared) is now the baseline for the next delta, and the key tags dropped with the skipped prefix are restated on the merged first segment, so media sequence numbers, AES IVs and keys stay right after the window slides past the first full playlist. A delta that cannot be merged is answered with `Error::DeltaNotMergeable` and a plain (non-delta) playlist request instead of mis-numbered segments.
- The `EXT-X-PRELOAD-HINT` part is requested once, not on every reload (it produced `DuplicateResource` and advanced the byte-range cursor each time).
- `on_key` with a wrong-length body now clears the in-flight key so the next reload requests it again.
- A failed init no longer lets a VOD stream end with `EndOfStream`; new `HlsClient::retry_init()` re-requests it (a live playlist's next reload already did), and `ensure_playlist_reload()` queues a plain reload when the core rejected a playlist before scheduling one.
- Encrypted segments waiting for a key are pruned with the window and capped at 64 MiB (oldest dropped, `Error::PendingKeyedOverflow`). Key maps are pruned with the window (a per-reload tokenised key URL no longer leaks), key ids are never reused, and a key whose segments left the window is fetched afresh when its URI returns.
- The non-blocking reload wait is capped at 60 s whatever `EXT-X-TARGETDURATION` claims.
- An init is requested again when only its `BYTERANGE` changes on the same URI. (An origin offering several different `EXT-X-MAP`s within one window is still served by the latest one only.)
- A segment URL re-signed on every reload (same path, different query) is no longer an origin restart.
- One unsupported or undecryptable segment (SAMPLE-AES, encrypted parts, ...) fails only that segment: it is skipped, the error is returned after the rest of the playlist was processed, and the reload is still queued. AES-128 with `EXT-X-MAP` is accepted: a map declared before the key is plain, a map after an AES-128 key is decrypted with it (explicit IV, else the Media Sequence Number of the first segment using it).
- Behaviour change: a segment whose `on_resource` failed (demux, decrypt) is requested again by the next reload instead of staying marked requested.
- `HlsClient` no longer rejects a whole playlist when clear segments follow a non-identity (FairPlay/Widevine) key: `METHOD=NONE` ends every `KEYFORMAT` (RFC 8216bis §4.4.4.4), and a segment covered only by an unsupported `KEYFORMAT` is skipped and reported after the rest of the playlist is processed.
- A per-segment `FRAME-RATE` measurement above 300 Hz is dropped (implementation-defined sanity cap), so one segment with broken timestamps cannot make the master playlist advertise an absurd `FRAME-RATE`.
