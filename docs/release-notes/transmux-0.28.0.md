# transmux 0.28.0

_Released 2026-10-31._

### Added
- Dolby Vision signalling for HEVC (issue #1428): `dovi` module with a typed `DoviDecoderConfigurationRecord` (symmetric parse/serialize, `DoviBlSignalCompatibilityId`), the TS `DOVI_video_stream_descriptor` (tag `0xB0`), and `TrackSpec::dovi`. The record is read from the PMT descriptor (a `stream_type` 0x06 stream with the DOVI registration descriptor and a descriptor of an HEVC profile is now an HEVC track instead of opaque data) and from the `dvcC`/`dvvC` box of an fMP4 sample entry (`dvh1`/`dvhe` entries are now read). The init segment writes `dvcC` (profile <= 7) or `dvvC` (profile > 7) with `hvc1` for a compatible base layer and `dvh1` for a non-compatible one (profile 5). Reserved bits of the record and descriptor are captured and re-emitted byte-exact, never a reason to drop signalling. Single-layer streams only; enhancement-layer carriage, `dvwC` and profile 10 are not implemented.
- HDR10+ dynamic metadata (SMPTE ST 2094-40, issue #1428): `hdr10plus` module with a typed `Hdr10PlusMetadata` (every syntax branch: up to three windows with elliptical selectors, both actual-peak-luminance tables, distribution percentiles, Bezier tone mapping, colour saturation weight; symmetric parse/serialize, byte-exact over all 259 SEI of the Tears of Steel fixture) and detection of the `B5 00 3C 00 01 04` T.35 header in HEVC prefix SEI. The wire syntax is reconstructed from FFmpeg and `hdr10plus_tool` because CTA-861-H Annex S is paywalled; the unit of `targeted_system_display_maximum_luminance` and the position of `color_saturation_mapping_flag` with more than one window are unconfirmed. Parsing is lenient: the ApplicationVersion 1 value constraints (Table 1 `V1`/`V2`, 9 percentiles, 9 anchors) are not enforced because real encoder output violates them. `TrackSpec::hdr10plus` is set from the first access unit of a TS or fMP4 HEVC track; the SEI passes through the fMP4/CMAF, TS and TS-HLS outputs unchanged. `DashPackager` emits `SupplementalProperty` `http://dashif.org/metadata/hdr` `SMPTE2094-40` on a video set whose Representations all carry HDR10+, plus `urn:dvb:dash:hdr-dmi` `ST2094-40` under a `urn:dvb:dash:profile:dvb-dash:*` profile. LL-DASH MPD output does not emit the property yet.

### Fixed
- The LL-HLS segmenter sizes its part target to the anchor's frame grid (issue #1621): when the first anchor frames show a near-constant duration and a whole number of frames below the configured target would fall under 85% of it (23.976 fps with 200 ms: 4 frames are 83%), the target is raised to the next whole number of frames (209 ms) and a part is cut on its last frame; otherwise the configured target is kept. `LlHlsSegmenter::part_target_ms` reports the value to advertise. A variable or unmeasurable frame duration keeps the configured target and the previous cut rule (RFC 8216bis section 4.4.4.9).
- `RtpStreamDepacketiser` now derives a monotonic `dts <= pts` for H.264 video with B-frames (issue #1611). RTP carries only the presentation time (RFC 6184 section 5.1), so every sample used to carry `dts == pts` in decoding order, which stepped backward under reorder. `dts` is now the sorted-PTS grid shifted by the reorder depth `N` (`pts` of the `(k-N)`-th frame in output order; the first `N` extrapolate by one frame period), with `N` from the SPS `max_num_reorder_frames` (ITU-T H.264 section E.2.1), 0 for Baseline and intra-only profiles, else measured over the first 8 access units. Steady state adds no latency; the start of a run holds `N` samples (8 when `N` is not declared). A stream that violates its assumed depth raises the new `RtpLossEvent::ReorderDepthExceeded` and keeps `dts` strictly increasing. Streams without B-frames are unchanged (`dts == pts`). New `decode_avc_reorder_depth` / `AvcReorderDepth`.
- `rfc6381_hvc1` / `HEVCDecoderConfigurationRecord::rfc6381` wrote a malformed HEVC codec string (`hvc1.02.00000004.L99.90` for a Main 10 level 5.1 stream): ISO/IEC 14496-15 uses the decimal `general_profile_idc` (with an `A`/`B`/`C` prefix for a non-zero profile space), the bit-reversed compatibility word in hex without leading zeros, and the decimal `general_level_idc`. It now gives `hvc1.2.4.L153.90`. This is a visible change to the `codecs` string of every HEVC output (HLS `CODECS`, DASH `codecs`, demo/Python bindings); the grammar is RFC 6381 plus ISO/IEC 14496-15 Annex E (paywalled, not transcribed; the corrected form is restated in ETSI TS 103 285 section 5.2.2, `private/specs-verified/dash/docs-specs/etsi-ts-103-285/ch05-video.md`). It is what an HLS `CODECS` attribute for a real HEVC stream needs (issue #1428).
- `PartInfo::independent` is now true when a part contains a sync sample of the anchor track, wherever it sits in the part, instead of only when its first sample is one (RFC 8216bis section 4.4.4.9: `INDEPENDENT=YES` when the Partial Segment contains an independent frame). Apple `mediastreamvalidator` reported the old behaviour as 'Partial segments that contain a sync frame SHOULD be marked INDEPENDENT' (issue #1599).
- `LlHlsSegmenter` no longer emits a Partial Segment in which the anchor track contributes no time (issue #1597). When audio or teletext lagged the video, the part that drained the last video sample before the next keyframe left only that lagging audio for the segment's final part, which reached the playlist as `EXT-X-PART:DURATION=0`. A part that would drain every anchor sample of a segment already long enough to close is now held until the next anchor sample, so the keyframe's cut merges it with the lagging samples into one final part (the part target is not exceeded, and the parts again add up to the segment duration, which Apple's validator also checks). A part whose anchor span is zero is skipped; its samples stay in the segment. No sample is dropped.

### Changed
- Explicit HE-AAC tracks (`TrackSpec::with_explicit_he_aac`, a DVB `AAC_descriptor` HE-AAC v2 value in the TS demux) now use the output sample rate (twice the core rate) as their media timescale, so every sample duration and timestamp doubles while presentation times are unchanged; `Track::with_explicit_he_aac` and `Sample::rescale_timescale` carry already-cut samples across.

### Added
- HDR10 static metadata (issue #1428): `HdrStaticMetadata`, `MasteringDisplayColourVolume`, `ContentLightLevel` (H.265 SEI payloadType 137 and 144, D.2.28/D.2.35), `TrackSpec::hdr`. `TsDemux` keeps the first SEI NAL carrying each message in the `hvcC` record (prefix SEI array after VPS/SPS/PPS, as ETSI TS 103 285 section 5.2.4 asks for `hvc1`), and `TrackSpec::new` derives `hdr` from it. `build_init_segment` writes `mdcv` then `clli` after `colr` in the `hvc1` entry (layout reconstructed from free sources, see `private/specs-verified/mpeg/hdr/isobmff-mdcv-clli-boxes.md`; byte-equal to the boxes GPAC writes for the same stream), and `Fmp4Demux` reads them back. The `colr` nclx box and HLS `VIDEO-RANGE` (PQ for transfer 16, HLG for 18) already followed the VUI colour description.
- `caption_detect` (issue #1428): `CaptionDetector` / `DetectedCaption` report which caption streams a video track carries, from A/53 caption data in H.264/HEVC SEI (via `caption_cc_data`) or MPEG-2 picture user data: CEA-608 field 1 / field 2 data (HLS `CC1` / `CC3`) and CEA-708 services 1 to 6 whose window the `cc-data` decoder has defined. Null padding triplets report nothing. New dependency on `cc-data` (with `decode`).

### Added
- Explicit HE-AAC signalling (issue #1428, Apple HLS rule: HE-AAC in fMP4 MUST use explicit SBR). `AudioSpecificConfig::with_explicit_he_aac(HeAacProfile)` builds the hierarchical form (`audioObjectType` 5 for v1 / 29 for v2, core rate, extension rate = 2x core, underlying AAC-LC) and re-expresses an already explicit one; `core_audio_object_type()` and `extension_sampling_frequency()` read it back. `CodecConfig::with_explicit_he_aac` / `TrackSpec::with_explicit_he_aac` rewrite an AAC track's `esds` (RFC 6381 becomes `mp4a.40.5` / `mp4a.40.29`; `sample_rate` becomes the SBR output rate, the track timescale stays the core rate; v2 reports 2 channels). New `HeAacProfile` enum (`name()`, `Display`).
- `AudioMetadata::he_aac`: `Some(HeAacProfile::V2)` when a PMT `AAC_descriptor` (tag 0x7C) declares an HE-AAC v2 `component_type` (EN 300 468 Table 26: `0x43 0x44 0x45 0x46 0x49 0x4A`; Parametric Stereo always rides on SBR), else `None`. The TS demuxers apply it: such an ADTS AAC track is emitted with explicit hierarchical PS signalling (`mp4a.40.29`). The HE-AAC v1 rows (`0x01 0x03 0x05 0x40 0x41 0x42 0x47 0x48`, and `0xA0`) are deliberately NOT acted on: Table 26 note 7 says plain AAC-LC streams must use those same values, so they do not show SBR is present. HE-AAC v1 is reachable only through an explicit override (`TrackSpec::with_explicit_he_aac`, multimux `audio_profiles`). Output is byte-identical when no descriptor says HE-AAC v2.
- `AudioSpecificConfig::samples_per_frame`: samples per AAC frame from the `GASpecificConfig` `frameLengthFlag` (ISO/IEC 14496-3 §4.4.1), `None` for object types or HE-AAC signalling it does not cover.
- `RtpStreamDepacketiser::set_track_config` replaces a track's codec configuration after SETUP (for dimensions learned from an in-band parameter set).
- `avc_sps_dimensions` and `avc_access_unit_dimensions`: the cropped output size of an H.264 SPS (the rule the TS demuxer uses for `TrackSpec` dimensions), and the same from the first SPS in a length-prefixed access unit.
- `LlHlsSegmenter` follower-cut mode (issue #1428 slice 2a): `CutPlan`/`PartCut` external-cut input and `follow()` so an audio-only segmenter cuts segments and parts where the (video) leader cut, with the leader's sequence numbers; the leader exposes its cuts via `record_cuts()`/`take_ready_cut_plans()` (absolute decode times of the anchor's segment and part starts), leaving `PartInfo`/`SegmentInfo` unchanged. A sample belongs to the segment/part it starts in; boundaries are converted with exact integer ceiling rescale; a segment or part with no follower sample starting in it is not emitted; the pending buffer is bounded.
- `LlHlsSegmenter::set_timeline_origin` (issue #1428 slice 2b) aligns a follower with its leader: the first segment each track emits in follower mode starts its `tfdt` at that track's first sample's decode time minus the shared origin (floored at 0), and a segment that follows a silent stretch (no sample of that track in an earlier leader segment) re-anchors the same way instead of continuing contiguously. A leader never consults it; default output is unchanged.
- `LlHlsSegmenter` part-level incremental cuts (issue #1428 part-level audio): a leader opted in with `record_part_cuts()` hands out each part boundary as it closes via `take_ready_part_cuts()` (`PartCutReady { msn, part_index, start_dts, timescale }`), independent of `record_cuts()`/`take_ready_cut_plans()`; a follower cuts matching parts via `follow_part()` as soon as a buffered sample starts at or after the next boundary (holding otherwise, bounded by the pending cap, typed error on overflow), and a `follow_part` for a later segment closes the open one at that boundary. `follow()` keeps working for whole-segment plans; incremental parts and segments are identical to whole-segment follow.

### Fixed
- `RtpStreamDepacketiser`: an RFC 3640 `AAC-hbr` packet aggregating several access units gave all of them the packet's `pts` and every non-final one duration 0. The group's step to the next timestamp is now divided across its AUs.
- `RtpStreamDepacketiser`: access units no longer get duration 0. Under B-frame reorder the step to the next AU in wire order is zero or negative, so a stream joined mid-GOP (a P frame followed by earlier-presented B frames) emitted zero-duration samples; a reordered H.264 track now resolves each AU against a small window of presentation timestamps (duration = step to the next presentation instant; the window is the largest wire-order distance observed between an AU and its presentation predecessor, capped at `MAX_REORDER_DEPTH` = 16 AUs, so a stream with no reorder holds nothing extra; drained by `flush`). A trailing or flushed AU takes, in order, the last real per-AU duration, the smallest positive timestamp step, then the stream's own declared timing (H.264 SPS VUI `timing_info`; AAC `AudioSpecificConfig` frame length). With none of these the AU is held, never given an invented duration, and is not emitted at end of stream. An aggregated group whose delta is smaller than its AU count uses the declared per-AU duration, or is not emitted. The first AU of a track that is reordered from its second AU keeps the forward step it was emitted with.

### Changed
- `StreamingTsHlsSegmenter::update_track` (issue #1425) now returns `Result<UpdateTrackOutcome>` (`Changed`/`Unchanged`/`Unknown`; an unknown `track_id` is now `Unknown` rather than an error) instead of `Result<bool>`; discontinuity arming compares typed fields only (audio sample rate / channel count / AudioSpecificConfig bytes; video timescale + display) instead of a `Debug` string of the whole `CodecConfig`, so a codec-config refresh (e.g. new SPS) with unchanged geometry/timing no longer arms a discontinuity. `PartialEq`/`Eq` derived on `CodecConfig` and `TrackSpec`. Breaking change for callers matching on the boolean.

### Fixed (G1)
- **`StreamingTsDemux` now harvests valid H.264/HEVC parameter sets from a damaged access unit.** A continuity gap or truncated PES used to drop the whole access unit *and* its SPS/PPS(/VPS), so a lossy start waited ~4 MB for the first usable init segment. Valid parameter sets are now taken from the damaged unit (and its config resolved when the track is still probing), while the damaged slice data is still dropped and the unit still counts as `InputDegraded` (invalid parameter sets stay ignored, #1171). `InputDegraded::InvalidParameterSet` is emitted for any rejected set, unchanged.

### Fixed (DASH-pull adoption)
- **`Fmp4Demux` takes a sample's duration, flags and size from the init movie's `trex` when neither the `trun` nor the `tfhd` gives one** (ISO/IEC 14496-12 section 8.8.7). A packager that declares its sample durations once in `trex` and writes `trun` entries with sizes only (GPAC does for a fragment of equal-length samples) produced samples of duration 0 that all shared the fragment's first `dts`, and, because the flags default of every sample was 0, marked every sample a sync sample. Found by playing GPAC's real multi-Period output (`fixtures/dash/multiperiod-restart/`) through `multimux`'s DASH pull. A `trex` size of 0 is not applied (writers use it for "not declared"). Covered by `tests/fmp4_trex_defaults.rs` on that real fixture.

### Added (round-9 audit F1)
- `IdrWait` and `StreamingTsHlsSegmenter::{with_idr_fallback, fall_back_to_any_rap, idr_fallback_active}`: a bounded fallback for `SegmentCutPolicy::IdrOnly`. Open-GOP H.264 (recovery-point SEI, zero IDR NALs) never delivers the IDR the policy waits for; after `bound` of dropped anchor media the segmenter cuts on any sync sample for the rest of the stream. Without `with_idr_fallback` the wait is unbounded as before. `IdrWait::observe_dropped` is the shared media-time accounting for callers that gate samples before the segmenter.

### Fixed (round-9 audit F2)
- **`StreamingTsHlsSegmenter` holds a cut for lagging audio.** A live multiplex delivers audio after the video it accompanies, so cutting the instant the anchor reached its next sync sample closed each segment with however much audio had arrived (1.15 s to 1.34 s of audio against 1.28 s of video on the zenith captures), which Apple's `mediastreamvalidator` reports as "Playlist vs segment duration mismatch". The cut is now held until every audio track that has delivered media holds a sample at or past the boundary, bounded by one second of further anchor media (`CATCH_UP_MAX_SECS`); a segment `EXTINF` still equals its video span. Pushes that already interleave by time cut exactly as before.

### Fixed (round-9 audit F6)
- **Box walkers no longer panic on an untrusted `largesize` that overflows `usize` arithmetic.** `find_config_box` (`off += size`, libFuzzer `transmux_sample_entries` crash), the `stsd`/`dref` entry walks, and the `stsd`/`dref`/`cenc`/subtitle/`webm` child walkers now clamp every extent to the bytes present (`box_types::child_extent_in`) and use checked/saturating advances; `parse_box` no longer truncates a `u64` size on 32-bit targets; the progressive chunk cursor saturates. Reachable through hls-runtime init validation (so `broadcast-client`).

### Fixed (round-9 audit F7)
- `LlHlsSegmenter` keeps cutting parts after a segment passes its target duration while it waits for the next keyframe. The part boundary used to be suppressed past the target, so every sample until the next IDR piled into the segment's final part (0.28-6.04 s against a 0.2 s `PART-TARGET` on real TS captures), breaking RFC 8216bis §4.4.4.9. The final part is now the short remainder. A single source sample longer than the part target still cannot be split.

### Added (round-6 audit F7)
- `CodecConfig::is_video()` is public: true for every video codec the IR carries (AVC, HEVC, VVC, AV1, VP9, VP8, MPEG-2 video), the counterpart of `audio_sample_rate().is_some()`. A consumer no longer has to infer "video" from `LiveJoin::for_config`, which is `None` for AV1, VP9, VP8 and MPEG-2.

### Added (round-6 audit F1)
- `SkippedTrack::track_id: Option<TrackId>` (+ `SkippedTrack::with_track_id`): the skipped `trak`'s `tkhd.track_ID`, set by `Fmp4Demux` and `ProgressiveDemux`, so a consumer can report one drop per track id. `None` for a record with no track header to name (the `CencDecryptor::demux` skip records).

### Fixed (round-5 audit F3/F6)
- **`StreamingTsDemux` no longer holds every resolved track back behind one stuck PID until `finish()`.** A `Probing` head used to stop `try_promote_ready` for all later PIDs of the whole multiplex, so a short or sparse multi-program capture (`private/fixtures/csa/csa2-plain.ts`, tsduck `test-062.ts`) emitted nothing until `finish()` and a live source stayed `Establishing` forever. An unresolved head now blocks only the PIDs of its own program (PMT order within a program is unchanged), and a head that cannot be a legitimate wait is stepped over, still probing and announced by a later `TrackAdded` if it resolves: `STUCK_HEAD_OWN_BYTES` (2 MiB of its own payload without a single access unit: scrambled or unframeable video never grows the byte-capped backlog) and, for non-video heads only, `STUCK_HEAD_INPUT_PACKETS` (4 MiB of input since the PID was declared). A video head that does produce access units is still bounded by `MAX_PROBE_BACKLOG_BYTES`. **Behaviour change for live consumers:** track ids follow resolution order across programs, not PMT order. The batch `TsDemux` (`demux`/`unpackage`) keeps strict PMT order, so `track_id_baseline` is untouched.

### Added
- `StreamingTsDemux::with_strict_pmt_order()`: the pre-fix promotion policy (global PMT order, no new step-over bounds) for callers that hold the whole input and `finish()`.
- `StreamingTsDemux::release_silent_heads()`: the caller declares the input so far is a complete self-contained unit (an HLS segment), so a PID its PMT declares that sent no payload packet is absent, not late, and stops holding back its program (a parked-bytes bound a short unit never reaches).
- `StreamingTsDemux::restart_timeline()`: a new, unrelated timeline begins (HLS `EXT-X-DISCONTINUITY`). Flushes the old timeline's tails like `finish()` but abandons nothing; resolved tracks keep their id, config and parameter sets, per-PID timing (33-bit unwrap, frame periods, audio anchor and carry, in-flight PES, continuity counters) and PMT versions are reset, and unresolved PIDs keep probing without their old-timeline backlog. A fresh demuxer re-probing from the new timeline alone lost every PID whose parameter sets were not in it.

### Added
- **`SegmentCutPolicy` for the streaming TS-HLS segmenter (issue #1425, Apple HLS Authoring Spec 7.4).** New public `SegmentCutPolicy { AnyRap, IdrOnly }` (non-exhaustive, `name()`, `Display`, serde, default `AnyRap` so existing behaviour is byte-for-byte unchanged) selected with `StreamingTsHlsSegmenter::with_cut_policy`. `IdrOnly` cuts only on an H.264 IDR slice or an HEVC `IDR_W_RADL`/`IDR_N_LP` picture (no CRA/BLA, recovery-point SEI or SPS-only heuristic); the segmenter drops every access unit until the anchor's first IDR (and again after `mark_discontinuity`, which then closes the pre-gap segment at the resync IDR and flags the segment it opens), counting anchor drops in `dropped_leading_aus()`. New `is_idr_nal` / `access_unit_is_idr` helpers. `TsHlsPackager` (batch) is unchanged. Segmenters do not yet see track updates, so the ASC-change (2.11) and frame-rate-change (8.14) discontinuities are not signalled (tracked on #1425).
- **DASH-IF ingest template matcher (P1).** New public `SegmentTemplate::match_url(template, candidate, known_representation_ids) -> Option<TemplateMatch>` reverses `SegmentTemplate::resolve` for ingest path classification: extracts `$RepresentationID$`/`$Number$`/`$Time$`/`$Bandwidth$` from a resolved URL, with `%0Nd` width fidelity and unique-match disambiguation. The internal tokenizer is now shared by `resolve` and `match_url` (byte-identical `resolve` behaviour).
- **HEVC frame rate now also uses VPS timing.** `decode_hevc_vps_timing` parses `video_parameter_set_rbsp` timing (`vps_num_units_in_tick`/`vps_time_scale` when `vps_timing_info_present_flag`) per `transmux/docs/codec/hevc-vps-timing.md`; `nominal_frame_rate` reads the first VPS array (nal_unit_type 32) from the hvcC and falls back to VPS timing when the SPS VUI carries none (SPS timing still wins; VPS HRD not used, so at most tier B). Applying the inheritance when the SPS has no VUI at all is an inference (doc §4).

- **Nominal frame rate now covers HEVC.** `transmux::nominal_frame_rate(config) -> Option<(u32, FrameRateBasis)>` returns the nominal frame rate in millihertz plus its basis (normative vs. convention), per `transmux/docs/codec/vui-timing-frame-rate.md` §1.4/§2.7. H.264 `time_scale / (2 * num_units_in_tick)` (normative when `fixed_frame_rate_flag == 1`, convention otherwise); H.265 normative from HRD `fixed_pic_rate_within_cvs_flag` (`ClockTick * (elemental_duration_in_tc_minus1 + 1)`, halved for `field_seq_flag == 1`), convention `vui_time_scale / vui_num_units_in_tick` when no fixed-rate info and `field_seq_flag == 0` and `frame_field_info_present_flag == 0`. New `AvcVuiTiming`/`HevcVuiTiming` (non-exhaustive) and `decode_avc_vui_timing`/`decode_hevc_vui_timing` (HRD walk included); `nominal_frame_rate_millihertz` is now a thin wrapper. `HevcSpsInfo::fps` doc corrected (convention tier only).
- **HLS `FRAME-RATE` source helper.** New public `transmux::nominal_frame_rate_millihertz(config: &CodecConfig) -> Option<u32>` returning the nominal frame rate in millihertz derived solely from an SPS's VUI timing (H.264 and now HEVC). AVC/H.264: `round_half_up(1000 * time_scale / (2 * num_units_in_tick))`; HEVC as above. Codecs without VUI timing, or `num_units_in_tick == 0`, or overflow yield `None` — never invented or guessed from sample durations.

### Added
- **HLS master playlist `RESOLUTION` (display-geometry Q8).** New public `transmux::presentation_size(display, coded_width, coded_height) -> (u32, u32)` returning the square-pixel presentation size (cropped output, rescaled by SAR) in whole pixels (16.16 value rounded to nearest); `tkhd_presentation_size` shares its core so the two cannot drift. `tkhd` bytes are unchanged.
- **DASH MPD advertises display geometry (design `docs/display-geometry/DESIGN.md`, Phase 4c).** `DashPackager` (and `LlDashPackager`, which wraps it) now writes `@sar="w:h"` (gcd-reduced, including `1:1`) on every video `Representation`, derived from `TrackSpec::display.sample_aspect_ratio()` (SPS VUI via the Phase 1a API; unknown/unspecified SAR yields no attribute), placed after `@frameRate`; and `@par="w:h"` (picture aspect ratio `(width*sar_w):(height*sar_h)`, gcd-reduced) on a video `AdaptationSet` only when every Representation in the set yields the same value (otherwise omitted). The trick-mode Representation is unchanged (no `sar`; `TrickModeRepr` keeps its public fields). Semantics follow ISO/IEC 23009-1:2022 Table 5/Table 14 (`@par` = `(@width*sarx):(@height*sary)`; `@width`/`@height` stay the cropped sample counts, the pixel shape lives in `@sar`) and ETSI TS 103 285 v1.4.1 §4.4, transcribed in `docs/specs/dash/23009-1/dash-23009-1-2022-aspect.md` (the 2026 6th edition is paywalled and was not checked). AdaptationSet/Representation MPD bytes therefore change for anamorphic or square-pixel video input.

- **Init-segment mux writes display geometry (design `docs/display-geometry/DESIGN.md`, Phase 4a-1).** `pipeline::build_trak` now appends a `pasp` (`PixelAspectRatioBox`) to AVC/HEVC sample entries when `TrackSpec::display.sample_aspect_ratio()` is specified and not 1:1 (hSpacing/vSpacing = the signalled SAR terms), and a `colr` (`ColourInformationBox`, colour_type `nclx`) when a colour description was signalled (primaries/transfer/matrix = the enums' `.code()` widened to u16, full_range_flag = the signalled full-range flag). Order after the codec config box: `pasp` then `colr`. Square-pixel, colour-unsignalled input produces byte-identical output (no box written); inferred defaults are never invented. `tkhd` width/height are now the cropped output size rescaled for the sample aspect ratio as 16.16 (see the Phase 5 entry below). Init-segment bytes therefore change for anamorphic or colour-signalled AVC/HEVC input (design Q9).

- **MPEG-2 video display geometry, AFD and bar data (design `docs/display-geometry/DESIGN.md`, Phase 3b).** New `h262` module: `DisplayGeometry::from_mpeg2_es(&[u8])` parses the first `sequence_header()` (H.262 §6.2.2.1), its `sequence_extension()` size extension (§6.2.2.3) and `sequence_display_extension()` (§6.2.2.4), and derives the sample aspect ratio from Table 6-3 + §6.3.3 (4:3 on 704x480 -> 10:11, 16:9 on 704x576 -> 16:11, 16:9 on 720x576 -> 64:45, 2.21:1 on 720x576 -> 221:125), expressed as `AspectRatioIdc::Square` or `AspectRatioIdc::ExtendedSar` (reduced); aspect 0 and 5..=15 are unspecified. `DisplayGeometry` gains a `mpeg2` marker (`is_mpeg2()`) so the inferred colour is codec-aware: absent extension / `colour_description` yields BT.709 1/1/1 for MPEG-2 (H.262 §6.3.6) and stays 2/2/2 for H.264/H.265. New `mpeg2_display::Mpeg2DisplayTracker` folds each MPEG-2 access unit (sequence header, picture header, `extension_and_user_data(2)` `DTG1` / `GA94`+0x06 user data) into the existing `DisplayChanged` / `Sample::display` machinery under the H.262 persistence rule (AFD and bar data last until the next `sequence_header()` or a new AFD, independent of `AfdPersistence`; bar data clears on a new AFD), and `from_codec_config` reads an `esds` that carries a sequence header. Both TS demux paths tag MPEG-2 samples and raise the per-AU events in order. `bar_data_from_t35_payload` accepts the MPEG-2 `DVB1_data()` body through the new `bar_data_from_ga94_payload`.

- **Demux-side display geometry (design `docs/display-geometry/DESIGN.md`, Phase 4a-2).** `track_spec_from_trak` (shared by `Fmp4Demux` and the progressive MP4 path) now overlays container-level `pasp` / `colr nclx` from an AVC/HEVC sample entry onto the SPS-derived `TrackSpec::display`: `colr nclx` overrides the bitstream colour (primaries/transfer/matrix/full_range; video_format kept if a video_signal was signalled, else Unspecified; code points above 255 are ignored), and a `pasp` fills in an unspecified VUI sample aspect ratio (Square idc when the reduced ratio is 1:1, otherwise Extended_SAR with the gcd-reduced pair; on a specified-vs-specified conflict the VUI SAR is kept because the available ISO/IEC 14496-12 §12.1.4 text does not define precedence). When the SPS yielded no display, one is created from the visual width/height plus the applicable SAR/colour. AVC/HEVC only; entries without either box are byte-for-byte unchanged.

- **fMP4 in-band display tagging (design `docs/display-geometry/DESIGN.md`, Phase 2b).** `Fmp4Demux::unpackage` now tags every sample of an in-band track (`avc3`/`avc4`/`hev1` sample entry) with `Sample::display`, running a per-track `SpsTracker` over the samples in decode order (length-prefixed NALs converted to Annex B for observation only; stored sample bytes unchanged). Out-of-band entries (`avc1`/`hvc1`) keep the existing `display == None` per sample and byte-identical output. The tracker is seeded from the track's `TrackSpec.display` (init avcC/pasp/colr overlay) and the same sample-entry overlay (pasp fill-in, colr nclx override) is applied to every tag via the shared `overlay_sample_entry_geometry` helper, so track-level and sample-level geometry agree. A sample whose length prefix overruns its data does not panic and keeps the previous tag.
- **Program Stream (PS) per-AU display tagging (design `docs/display-geometry/DESIGN.md`).** `PsDemux` now tags every video sample with `Sample::display`: H.264 via `SpsTracker` (seeded from the recovered avcC geometry) and MPEG-2 via `Mpeg2DisplayTracker` (seeded from the first `sequence_header()`), in decode order with the same `Arc`-sharing behaviour as the TS/fMP4 paths. Audio and other tracks keep `display == None`. MPEG-1 Program Streams produced by ffmpeg `-f mpeg` are now accepted by a direct PES scan (the MPEG-2 pack layer rejects them).

### Changed
- **DASH `AdaptationSet@id` is now an unsigned integer** (ISO/IEC 23009-1:2022 Table 5, printed p. 41). Regular sets keep their deterministic sequence (`0`, `1`, `2`, ...). Previously `t0`, `t1`, ... (rejected by `xs:unsignedInt`).
- **`TrickModeAdaptationSet.id` and `.main_adaptation_set_id` changed from `String` to `u32`** (breaking, 0.x minor-class). Migration: pass integers (e.g. `id: 7, main_adaptation_set_id: 0`).
- **`TRICKMODE_SCHEME` changed from `urn:mpeg:dash:trickmode:2016` to `http://dashif.org/guidelines/trickmode`** (DASH-IF IOP v4.3 SS3.2.9).
- **AdaptationSet child-element order now follows the 6th-edition schema**: `ContentProtection` and `InbandEventStream` precede `Role`/`Representation`; LL-DASH `UTCTiming` emitted after `Period`.

- **AFD and bar data for H.264/H.265 (design `docs/display-geometry/DESIGN.md`, Phase 3a).** `ir::display` gains `ActiveFormatDescription` (16 codes, Table B.5), `BarData`, `UserDataCarriage`, `ActiveFormat` and `AfdPersistence` (`UntilReplaced` default / `ResetAtRandomAccess`), and `DisplayInfo` gains `active_format: Option<ActiveFormat>` (additive `with_active_format`); `DisplayChangeSet` gains `afd` and `bar_data`. A shared `user_data` module parses `afd_data()` (`DTG1`) and `bar_data()` (`GA94` + 0x06) from H.264 SEI NAL type 6 and H.265 prefix SEI only (suffix SEI ignored). Persistence is configurable on both demuxers via `with_afd_persistence`. AFD is folded into the existing per-AU `DisplayInfo`/`DisplayChanged` machinery with merged change sets and `random_access` as the AU's own. MPEG-2 picture user_data landed in Phase 3b (see above).

### Fixed
- **A `DisplayChanged` parked for an access unit was released before the *previous* access unit's sample.** `PendingOneBehind::pending_events`' doc (and design §6.5) say a change is released with its own sample; `advance_one_behind` instead pushed it immediately, before the sample of the access unit already in the one-behind slot, labelling one picture with the new state (the MPEG-2 per-AU tracker is the first consumer that parks a change on every event). It now stays parked on the new slot. The equally early `TrackUpdated` push is a separate, pre-existing behaviour and is unchanged here.
- **Documentation and regression test for `TrackUpdated` at a programme/slate switch (#1380).** The 0.27.7 release note described the two `TrackUpdated` events seen on the slate-switch captures as a pre-existing duplicate caused by the track re-probe. That diagnosis was wrong: they are two *independent* events. The broadcaster's PMT lists fewer `es_info` descriptors on the slate (9 vs 3 on the real captures), which raises the descriptors-only `TrackUpdated` (#774, codec config unchanged) when the PMT is processed; the new SPS/PPS then raises the config-change `TrackUpdated` (r04-W51) immediately before `DisplayChanged` and the first new-geometry sample. Both are correct and each carries the full current `TrackSpec`; nothing is emitted twice. `DemuxEvent::TrackUpdated` now documents all three causes (it previously omitted the TS in-band config change), `docs/display-geometry/DESIGN.md` §6.1/§6.5 name the PMT cause, and `tests/track_updated_causes.rs` pins the behaviour on the three real captures (the two events, their order, their contents, and the strict placement of the config one) and on the public `h264-two-resolutions.ts` (exactly one).
