# `fixtures/hls/` — provenance manifest

Every fixture in this tree is listed below with its source, when it was
added, its licence/redistribution status, and what it is *for*. If a fixture
starts failing and this manifest can't explain where it came from, that's a
bug in this file — fix it before touching the fixture.

Parsed and asserted by `transmux/tests/hls_fixture_corpus.rs` (`cargo test -p
transmux --test hls_fixture_corpus`). See that file's module doc for the
current pass/fail table — this file is provenance, that file is behaviour.

## Tier 1 — spec test vectors (`fixtures/hls/spec/`)

Source: `ll-hls-runtime/docs/examples.md`, itself a verbatim transcription
(commit `a07124ae`, 2026-08-01, issue #867) of §9 "Playlist Examples" from
**draft-pantos-hls-rfc8216bis-22** (IETF Internet-Draft, 1 May 2026),
source lines 4608–5023 of `specs/ietf_draft_pantos_hls_rfc8216bis.txt`.
Extraction/commit date into this fixture tree: 2026-08-02.

Licence/redistribution: IETF Internet-Drafts are governed by
[BCP 78](https://www.rfc-editor.org/info/bcp78) — freely reproducible in
full without modification (which these are, modulo the transcription's own
documented whitespace normalization — see `examples.md` header). This is
example/illustrative text, not the operative spec text.

These are **authoritative**: written by the spec's own authors. If our
parser disagrees with one, our parser is wrong (subject to the two
documented exceptions below).

**9.8 and 9.9 are deliberately NOT committed.** Both are explicit fragments
in the spec's own prose, not complete playlists:

- §9.8 — the spec says "In this example, only the EXT-X-SESSION-DATA is
  shown"; the excerpt has no `#EXTM3U` header at all.
- §9.9 — not even a tag, just an isolated `CHARACTERISTICS=".."` attribute
  value shown to illustrate that attribute's comma-separated grammar.

Neither begins with `#EXTM3U`, so neither is a playlist a parser could ever
be expected to accept — committing either as a `.m3u8` fixture would just
be an always-red test with no signal. (Their content is fully reproduced,
with this same reasoning, in `ll-hls-runtime/docs/examples.md` §9.8/§9.9.)

### Line-continuation joining (9.6, 9.7, 9.10, 9.12)

The spec uses a trailing `\` plus indentation purely as an editorial
line-wrap convention for the Internet-Draft's fixed page width — its own
preamble to §9 says so explicitly ("In some examples a '\' is used for
readability to indicate that the tag continues on the following line.").
A real HLS playlist has each tag on one physical line; a real parser would
see a backslash-terminated line as a broken tag, not a continuation.

Four examples carry this artifact: **9.6**, **9.7**, **9.10**, and **9.12**
(9.8, already excluded above, also has it but doesn't matter). For each:

- The committed `.m3u8` is the **joined** form: continuations resolved
  (trailing `\` removed, the next line's alignment-only leading whitespace
  stripped, and the two concatenated with no added separator — verified by
  hand against each attribute list / hex string so no token boundary changes).
  This is what `hls_fixture_corpus.rs` parses.
- A sibling `.rfc-verbatim.txt` — **not** `.m3u8`, so it is not picked up by
  the test's directory-completeness check or parsed by anything — preserves
  the backslash-continued form exactly as printed, so the editorial-vs-real
  distinction stays visible and auditable.

9.10 additionally contains the spec's own `...` elision lines (both a
standalone playlist line and mid-hex-string continuations in the SCTE-35
payloads) — those are preserved as-is in both the joined and verbatim forms;
they are a different artifact from the continuation backslashes (see
Findings below).

### JSON manifests (9.12, 9.13)

§9.12 and §9.13 each carry a Content Steering Manifest, which is **JSON, not
m3u8**. Committed as standalone `.json` files (`9.12-content-steering-manifest.json`,
`9.13-content-steering-pathway-clone-manifest.json`), validated as parseable
JSON (`python3 -m json.tool`) at commit time but not parsed by
`hls_fixture_corpus.rs` (that test is playlist-only; no Content Steering
Manifest parser exists in this crate yet). §9.13's prose "resulting URIs"
list (three example URIs after the JSON block, showing the effect of the
Pathway Clone) is documentation, not itself a fixture — not committed.

### Findings: which fixtures fail to parse, and why

`transmux/tests/hls_fixture_corpus.rs` parses all 10 committed spec `.m3u8`
files. **8 parse cleanly; 2 fail:**

- **`9.10-daterange-scte35.m3u8`** — `Error::HlsParse` at line 2, reason
  `"media segment URI with no preceding #EXTINF"`.
- **`9.11-low-latency-playlist.m3u8`** — same error shape, at line 3.

Root cause for both: the spec's own `...` elision marker (§9.10: "...Media
Segment declarations for 60s worth of media"; §9.11: elided
`#EXT-X-PART` tags "removed from earlier Parent Segments") is a bare line
that doesn't start with `#`, so the parser reads it as a Media Segment URI.
Since no `#EXTINF` precedes it, that's a hard parse error by the crate's own
(correct) rules.

**This is not a missing-tag gap for issue #872.** Every *tag* in both
examples that this crate doesn't structurally model — `EXT-X-KEY`,
`EXT-X-MEDIA`, `EXT-X-CONTENT-STEERING`, `EXT-X-DATERANGE` (incl. its
`SCTE35-OUT`/`SCTE35-IN` sub-fields) — is either preserved verbatim
(`MediaPlaylist::extra_tags`) or silently skipped (`MasterPlaylist`, which
has no extra_tags field), never rejected. §9.10 and §9.11 fail purely
because they are intentionally-incomplete excerpts of a longer playlist, not
because of unimplemented tag support. No real encoder emits a literal `...`
segment URI, so this is not evidence of a parser defect either — it's an
artifact of committing spec prose byte-for-byte. Recorded here rather than
worked around, per the issue's instruction not to weaken the assertion, not
implement missing tags, and not delete the fixture.
